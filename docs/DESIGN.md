# Code++: A Notepad++-Style Cross-Platform Editor — Design

**Goal:** a cross-platform, Notepad++-inspired text editor with **Windows-class startup and editing performance**, written in Rust with Scintilla as the editing engine and native UI per platform.

**Compatibility goal:** binary-compatible with existing Notepad++ plugins on Windows; source-compatible (recompile) on Linux and macOS.

---

## 1. Goals and Non-Goals

### 1.1 Goals

- Notepad++-equivalent editing experience: tabs, syntax highlighting, find/replace, find-in-files, encoding control, EOL control, session restore.
- Startup in **tens of milliseconds** on a warm-cache machine.
- Memory profile dominated by buffer text, not framework overhead.
- Native UI on each platform (Win32, GTK, Cocoa) — no Electron, no embedded browser, no GC runtime.
- Plugin host that accepts existing **Notepad++ DLL plugins unchanged** on Windows, and the same plugin source recompiled on Linux/macOS.

### 1.2 Non-Goals

- Reimplementing Scintilla. We use it via FFI; we do not fork or port it.
- LSP, project-wide indexing, Git integration, AI assist — out of scope for v1. Plugins may add them later.
- Web-based or mobile builds.
- A Rust-stable plugin ABI. Plugins speak C.

## 2. High-Level Architecture

### 2.1 Component graph

```text
                       app (bin)
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
       ui_win32      ui_gtk       ui_cocoa     (one selected at build time)
            │            │            │
            └────────────┼────────────┘
                         ▼
                       shell
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
         editor       plugin-host   core
            │            │            │
            ▼            ▼            ▼
      scintilla-sys   platform     (std only)
            │
            ▼
       Scintilla + Lexilla (C/C++, vendored)
```

**Direction is strictly downward.** No upward calls, no cycles. Higher layers hold handles to lower layers; lower layers fire events that higher layers subscribe to via channels (never via callbacks into higher crates).

### 2.2 Crate responsibilities

| Crate | Responsibility | Allowed deps |
| --- | --- | --- |
| `core` | Pure data + logic: session model, file I/O, encoding/EOL detection, settings, history bookkeeping. **No UI, no Scintilla, no platform code.** Headless-testable. | `std`, small utility crates only |
| `editor` | Safe Rust wrapper over `scintilla-sys`. Owns nothing OS-specific beyond an opaque `EditorHandle` (newtype per platform under `#[cfg]`). | `scintilla-sys`, `core` (for shared types only — not for state) |
| `scintilla-sys` | **Our own** custom `-sys` crate. Raw FFI to Scintilla 5.x + Lexilla. Vendors the C/C++ source via git submodule and builds it with `cc`. **Not the unmaintained crates.io `scintilla-sys`.** | `cc` (build), `bitflags` |
| `platform` | OS-specific utilities: config paths, dynamic library loading, file watching, process info. | `std`, `windows`, `nix`, etc. behind `#[cfg]` |
| `plugin-host` | Loads N++-compatible plugin DLLs/SOs, owns the NPPM message dispatcher, exposes a strongly-typed Rust event bus to the rest of the app. | `core`, `editor`, `platform` |
| `shell` | Glue layer that owns `Session`, `EditorHandle`s, and the plugin host. Defines the `UiPlatform` trait that UI crates implement. | `core`, `editor`, `plugin-host`, `platform` |
| `ui_win32` | Win32 window, menus, tabs, dialogs, status bar. Implements `UiPlatform`. | `shell`, `windows` crate |
| `ui_gtk` | GTK equivalent. | `shell`, `gtk` (gtk3-rs) |
| `ui_cocoa` | Cocoa equivalent. | `shell`, `objc2`, `objc2-app-kit` |
| `app` | Thin binary: parses args, picks the UI backend at compile time, calls `shell::run()`. | `shell`, one of `ui_*` |

### 2.3 What moved and why

- The `UiPlatform` trait that the original draft put in `core` lives in `shell`. `core` must be buildable and unit-testable without any window system in scope.
- Plugin loading mechanics (`LoadLibrary`/`dlopen`) live in `platform`. The plugin **registry, lifecycle, and message dispatcher** live in `plugin-host`. The split keeps OS calls out of plugin-host's logic.
- `editor` does **not** depend on `core` for state, only for shared value types (e.g., `Eol`, `Encoding`). This breaks the cycle in the original draft.

## 4. External Native Dependencies

### 4.1 Scintilla and Lexilla — vendored and built from source

We do **not** depend on the crates.io `scintilla-sys` (last meaningful release is years stale, predates Scintilla 5.x's split into Scintilla + Lexilla). We ship our own.

- **Vendoring:** `crates/scintilla-sys/vendor/scintilla` and `vendor/lexilla` are git submodules pinned to specific Scintilla and Lexilla release tags (initial target: latest stable as of project start; tag pin is bumped deliberately, never floating).
- **Build:** `build.rs` compiles the C/C++ source with the `cc` crate. Per platform:
  - **Windows:** compile `scintilla/win32/*.cxx`, link `user32`, `imm32`, `ole32`, `oleaut32`, `msimg32`. Build static, link static. No `scintilla.dll` shipped.
  - **Linux:** compile `scintilla/gtk/*.cxx`, link against system GTK **3** (`pkg-config gtk+-3.0`). GTK 3 rather than GTK 4 is forced by upstream: Scintilla ships no GTK 4 backend. `vendor/scintilla/doc/ScintillaDoc.html` documents "GTK 2.24 and 3.x" only, the highest version guard in `gtk/` is `GTK_CHECK_VERSION(3,22,0)`, and the source uses APIs GTK 4 removed outright (`GdkWindow`, `gtk_widget_get_window`, `gtk_container_add`, `gtk_widget_set_events`, `gdk_window_get_origin`, `gtk_style_context_get_background_color`). Targeting GTK 4 would mean porting Scintilla's platform layer, which §1.2 rules out. GTK 3.24 is the final, API-frozen GTK 3 series, so this is a stable target — the same choice Geany and SciTE make. Also compile `gtk/scintilla-marshal.c` (plain C, so it needs its own `cc::Build`).
  - **macOS:** compile `scintilla/cocoa/*.mm`, link `Cocoa`, `QuartzCore`.
  - **Lexilla** is built the same way and statically linked into the same crate.
- **Output:** one static archive per target, exposed to `editor` as a single `extern "C"` surface.
- **Why static:** smaller distributable, no DLL-hell, identical loader hot path on every machine, supports the startup-time goal.

### 4.2 Direct-call API (the speed path)

Scintilla exposes two ways to send messages:

1. `SendMessage(hwnd, SCI_..., wparam, lparam)` — works always, costs a window-message round trip.
2. `SCI_GETDIRECTFUNCTION` + `SCI_GETDIRECTPOINTER` — returns a `(fn_ptr, instance_ptr)` pair. Calling the function pointer directly skips the message pump. **This is what gives Notepad++ its keystroke latency.**

`editor` obtains the direct-call pair once when each Scintilla control is created and stores it on the `EditorHandle`. Hot operations (`insert`, `replace`, `set_sel`, `text_length`, `get_text_range`, lexer state queries) go through the direct path. `SendMessage` is reserved for setup, cross-thread one-shots, and operations that must be ordered with the window message queue.

This must be in place from Phase 1 — retrofitting it later means rewriting every `editor` method.

### 4.3 Other native dependencies

- Windows: `windows` crate (Microsoft's official bindings), pinned minor version.
- Linux: `gtk`, `glib`, `gio` via **gtk3-rs** (`gtk` 0.18). Compile-time linked through `pkg-config`. The gtk3-rs crates are archived upstream, so `deny.toml` carries documented `[advisories] ignore` entries for them; GTK 3.24 is itself API-frozen, so there is nothing left for the bindings to track. See §4.1 for why GTK 3 and not GTK 4.
- macOS: `objc2`, `objc2-app-kit`.
- Cross-platform utilities: `notify` (file watching), `parking_lot` (locks), `crossbeam-channel` (cross-thread messaging), `bitflags`, `tracing` + `tracing-subscriber`, `serde` + `quick-xml` (session.xml).

All version-pinned in workspace `[workspace.dependencies]` and inherited by member crates.

## 5. Cross-Cutting Concerns

### 5.1 Encoding detection and preservation

- **BOM-prefixed:** UTF-8, UTF-16 LE, UTF-16 BE, UTF-32 LE/BE — trivial.
- **No BOM:** statistical detection in `core::encoding`. Step order:
  1. Try strict UTF-8 decode of the first 64 KiB. If valid and contains any non-ASCII byte, decide UTF-8.
  2. If pure ASCII, decide UTF-8 (lossless).
  3. UTF-16 without BOM heuristic: count zero bytes in even vs odd positions in the first 8 KiB. Strong skew in either direction → UTF-16 LE/BE.
  4. Fall back to system default codepage (CP1252 on Windows-en, GB18030 on Windows-zh-CN, etc.) via the `encoding_rs` crate.
- **Preservation:** the detected encoding is the default save encoding for that buffer. Changing it is an explicit menu action.
- **Conversion failures on save:** show a dialog with the offending bytes' positions, never silently lose data.

### 5.2 EOL detection and preservation

`core::eol::Eol = { Lf, CrLf, Cr, Mixed }`.

- Detected on first read by counting line endings in the first 64 KiB.
- Preserved on save unless the user explicitly changes it (Edit → EOL Conversion).
- `Mixed` is shown in the status bar with a warning glyph; saving as `Mixed` keeps each line's original ending.

### 5.3 External file change detection

- `platform::watch::Watcher` wraps `notify` and emits events on a `crossbeam_channel`.
- For each open file, `shell` registers a watch; on modification the UI thread asks: "Reload? Keep my version? Diff?" — same UX as Notepad++.
- Watching is per-file, not per-directory, to keep startup cost zero.

### 5.4 Cross-thread UI marshaling

Win32 (and the others) require window-handle operations on the thread that created the window. Workers cannot call `SendMessage` to a UI HWND safely, and they cannot touch Scintilla state directly.

Pattern, mandatory for every worker that produces a UI-visible result:

1. Worker pushes a typed message onto a `crossbeam_channel::Sender<UiTask>` owned by the UI thread.
2. Worker calls `PostMessage(ui_hwnd, WM_APP_WAKE, 0, 0)` (Win32) / `g_main_context_invoke` (GTK) / `dispatch_async` to main queue (Cocoa) to wake the UI thread.
3. UI thread's wake handler drains the channel and applies each `UiTask` (which may call into `editor` on the UI thread, where direct-calls are safe).

`shell` owns the `UiTask` enum and the channel ends. UI crates only know how to wake themselves; they do not invent their own marshaling.

### 5.5 Logging and diagnostics

- `tracing` throughout. Default subscriber is **off** in release builds (zero cost) and **on** when `--verbose` or `CODEPP_LOG=info` is set.
- One log sink: stderr in dev, rotating file in `%LOCALAPPDATA%\Code++\logs\` in release.
- Plugin host wraps every plugin call in a `tracing::span!` so misbehaving plugins are identifiable.

### 5.6 Testing strategy

| Layer | Test type |
| --- | --- |
| `core` | Unit tests, no FFI, no UI. Encoding detection, EOL detection, session round-trip, settings parse — all pure functions. |
| `scintilla-sys` | Smoke test: link, create Scintilla instance off-screen, send `SCI_INSERTTEXT`, read back via `SCI_GETTEXT`. Catches build/link regressions. |
| `editor` | Integration test: same as above, but exercising the safe wrapper and the direct-call path. |
| `plugin-host` | Loads `plugins/example-hello` and asserts the lifecycle messages fire in order. From Phase 4 m7 onward, also loads each preinstalled plugin (`cppmimetools`, `cppconverter`, `cppexport`) and asserts at least one NPPM round-trip per plugin (e.g. cppmimetools's base64 round-trip, cppconverter's hex→ASCII selection conversion, cppexport's HTML output containing the lexer-styled spans). |
| `tools/npp-plugin-test` | Loads a real, unmodified Notepad++ plugin DLL (e.g. NppExec) and verifies setInfo / getName / getFuncsArray succeed. Only runs on Windows in CI. |
| End-to-end | Manual smoke checklist in `docs/smoke.md` for each phase's demo. |

CI matrix: `windows-latest`, `ubuntu-latest`, `macos-latest`. Linux and macOS are build-only until Phase 5; Windows runs the full test suite from Phase 1.

## 6. Plugin System — Notepad++ Compatible from the Ground Up

### 6.1 Compatibility scope

- **Windows binary compatibility:** an existing Notepad++ plugin DLL (compiled against the public Notepad++ plugin headers) loads into Code++ without modification. Code++ exposes the same entry points, the same `NppData` struct, the same `NPPM_*` and `NPPN_*` messages, and the same Scintilla-message forwarding semantics.
- **Linux/macOS source compatibility:** the same plugin source compiles to a `.so`/`.dylib` with the headers we ship in `plugins/nppcompat-headers/`. Binary plugins are inherently platform-specific — there is no cross-platform binary plugin format and we will not invent one.

This is a significant surface. We implement it incrementally (see phases) but the ABI is fixed in Phase 3 and not broken thereafter.

### 6.2 Required plugin entry points

A Code++ plugin DLL must export, exactly as Notepad++ does:

```c
extern "C" __declspec(dllexport) void        setInfo(NppData);
extern "C" __declspec(dllexport) const TCHAR* getName(void);
extern "C" __declspec(dllexport) FuncItem*    getFuncsArray(int* nbF);
extern "C" __declspec(dllexport) void         beNotified(SCNotification*);
extern "C" __declspec(dllexport) LRESULT      messageProc(UINT, WPARAM, LPARAM);
extern "C" __declspec(dllexport) BOOL         isUnicode(void);
```

`NppData` carries the host window handle and the two Scintilla view handles, identical layout:

```c
typedef struct NppData {
    HWND _nppHandle;
    HWND _scintillaMainHandle;
    HWND _scintillaSecondHandle;
} NppData;
```

On Linux/macOS, `HWND` is replaced by an opaque `void*` newtype that maps to the platform's window handle. The header file abstracts this so plugin source stays portable.

### 6.3 Message ABI

Two message families flow through `messageProc`:

- **`NPPM_*`** — host control messages. Initial set covered in Phase 3:
  - File/buffer queries: `NPPM_GETCURRENTSCINTILLA`, `NPPM_GETCURRENTBUFFERID`, `NPPM_GETFULLPATHFROMBUFFERID`, `NPPM_GETBUFFERLANGTYPE`.
  - Editor actions: `NPPM_DOOPEN`, `NPPM_SAVECURRENTFILE`, `NPPM_SWITCHTOFILE`, `NPPM_RELOADFILE`.
  - UI: `NPPM_MENUCOMMAND`, `NPPM_GETMENUHANDLE`, `NPPM_SETSTATUSBAR`.
  - Path/version: `NPPM_GETNPPDIRECTORY`, `NPPM_GETNPPFULLFILEPATH`, `NPPM_GETPLUGINSCONFIGDIR`, `NPPM_GETNPPVERSION` (returns a Code++ version that is range-compatible with Notepad++ for plugin gating).
- **`SCI_*`** — Scintilla messages. Plugins commonly do `SendMessage(scintillaHandle, SCI_INSERTTEXT, ...)`. Because `scintillaHandle` is a real Scintilla `HWND` we created, these just work.

Notifications flow the other way through `beNotified`: `NPPN_READY`, `NPPN_TBMODIFICATION`, `NPPN_FILEOPENED`, `NPPN_FILESAVED`, `NPPN_FILECLOSED`, `NPPN_BUFFERACTIVATED`, `NPPN_LANGCHANGED`, `NPPN_SHUTDOWN`. Phase 3 ships the lifecycle ones; the long tail is filled in during Phase 4.

A coverage matrix lives in `docs/nppm-coverage.md` and is updated every time a new message is implemented. The matrix is the source of truth for plugin compatibility.

### 6.4 Lifecycle

1. App starts → `plugin-host` enumerates `%APPDATA%\Code++\plugins\*\*.dll` (Windows) / `~/.config/Code++/plugins/*/*.so` (Linux) / equivalent on macOS.
2. Loading is **deferred**: the host records the file path and registers menu placeholders. No DLL is mapped.
3. First time the user opens the Plugins menu, hovers a plugin entry, or fires a hotkey owned by the plugin, the host loads that DLL: `LoadLibraryW` → resolve six exports → call `setInfo(NppData{...})` → call `getFuncsArray` → install the menu items and shortcuts → fire `NPPN_READY`.
4. On subsequent file events, the host calls `beNotified` on each loaded plugin synchronously on the UI thread (matches N++ semantics).
5. On exit: `NPPN_SHUTDOWN` → unload.

### 6.5 Safety boundaries

- Plugins run in-process, same address space as the editor. Same as Notepad++: a buggy plugin can crash the app. Document this; do not pretend otherwise.
- Plugin calls are wrapped in a `tracing` span and a `catch_unwind` boundary on the Rust side so a panic inside Rust-written plugins doesn't unwind across FFI. C++ plugins that throw past their own ABI are out of scope (they're broken in N++ too).
- Per-plugin timeout for `beNotified`: log a warning if it exceeds 100 ms, but do not kill the plugin. Notepad++ doesn't either; behavior parity matters.

### 6.6 Preinstalled plugins — clean-room in-tree reimplementations

Notepad++ defaults ship with three preinstalled plugins — **mimeTools**, **NppConverter**, and **NppExport** — and Code++ wants the same out-of-the-box experience. Three in-tree plugin crates (`plugins/cppmimetools/`, `plugins/cppconverter/`, `plugins/cppexport/`) deliver that, built as `cdylib`s against Code++'s own N++-compatible plugin ABI. Beyond the user-facing default-set parity, three real plugins exercising the host's NPPM surface in three different ways are a far stronger ABI smoke test than `example-hello` alone — more dogfood, tighter feedback loop on host bugs.

That they happen to be in-tree clean-room reimplementations rather than bundled upstream binaries is also a licensing constraint, not just a preference: two of the three upstream plugins (`mimeTools`, `NppConverter`) are licensed **GPLv3**; the third (`NppExport`) ships without a license file, which under default copyright is "all rights reserved". Bundling either category inside Code++'s MIT-licensed release archive is a hard no:

- **GPLv3 plugins:** the plugin and the host are independent works at runtime — a user who downloads `mimeTools.dll` separately and drops it into the plugins directory is fine, the same way it works in N++ (no special arrangement required). The problem is **redistribution**: shipping a GPLv3 binary inside Code++'s release archive makes Code++ the distributor of a GPL-licensed work, and GPLv3's terms then govern what the distributor can do — terms that conflict with the MIT license under which Code++ as a whole is released. This mirrors the workspace's own `deny.toml` policy, which denies copyleft licenses on Cargo dependencies for the same redistribution reason.
- **Unlicensed plugins:** simply not legally redistributable.

So the decision: clean-room reimplement all three under MIT inside the Code++ workspace. The functionality is purely buffer-text transformation (encode/decode, hex/ASCII conversion, syntax-aware export) so the reimplementations are tractable. Users who want the upstream GPLv3 plugins can still install them by hand — runtime loading by the plugin host is the same as for any other third-party plugin and doesn't trigger any redistribution obligation on Code++.

## 7. Implementation Phases

### 7.1 The phase rule (read this first)

> **No phase is complete until a fresh `cargo run` of the platform binary demonstrates the phase's behavior end-to-end against the real underlying technology — real Scintilla messages, real Win32/GTK/Cocoa events, real disk I/O, real loaded DLL plugins. Stubs and mocks are acceptable only inside `core` unit tests, never in the integration path.**
>
> The "Demo" column for each phase is the acceptance test. If the demo does not run, the phase is not done — regardless of how much code was written.

This rule exists specifically to prevent the failure mode where layers are built in isolation and the wiring between them is "left for later" until it's no longer feasible.

**macOS m3c — tab-strip parity (landed).** The strip goes from "a row of buttons that select" to the strip the other two backends have: the shared `assets/icons/tab-save*.png` glyph replacing m3a's text bullet, a pin toggle drawing the same thumbtack polygon Win32 and GTK draw, middle-click-to-close, per-tab tooltips carrying the untruncated name, and drag-to-reorder.

Reorder is the part with no native affordance to inherit. `GtkNotebook` gives `ui_gtk` drag-reorder for free via `set_tab_reorderable`; `NSButton` offers nothing equivalent, and its own `mouseDown:` runs a tracking loop that does not return until mouse-up — so an ordinary target/action pair, which m3a used, has already lost the gesture by the time it fires. `TabButton` therefore overrides `mouseDown:` **without chaining to super** and pulls events off the queue with `nextEventMatchingMask:` itself, deciding click-versus-drag from what the mouse actually did. The consequence worth knowing is that the cell's push-on/push-off toggle never runs, so selection is painted from the model on every sync and never read back off AppKit's button state — the same "never infer selection from a signal" rule `ui_gtk`'s strip already documents. A rejected `move_tab` (dragging into or out of the pinned cluster) needs no undo path: the strip rebuilds from the model afterwards either way.

**The milestone opened with the systematic `ui_gtk`-versus-`ui_cocoa` call-site comparison that the run of user-reported bugs after m3b argued for, and it found two more of the same kind — both omissions rather than mistakes.** First, the dirty marker consulted `SCI_GETMODIFY` alone. A buffer restored from a crash-recovery backup sits at its Scintilla save point with no copy on disk, so editing one character and undoing it returned the document to that seeded save point and the marker flipped to clean for a buffer existing only in memory. §7.4 records exactly this as an open Win32 bug and names `ui_gtk` as the correct one because it ORs `Shell::is_unsaved_restore`; Cocoa had inherited the Win32 shape. No data was ever at risk — `Shell::tab_needs_backup` ORs the same id set, so the backup is retained regardless — but the indicator was wrong, and m3b's notification wiring had made it worse by giving `refresh_tab_chrome` a live value to overwrite the restore flag with. Second, nothing recorded the outgoing buffer's dirty state before a tab switch moved `active_tab`, so an inactive tab could keep a stale marker; `ui_gtk` has `capture_active_dirty` for precisely that, and the ordering is load-bearing in a way that is invisible at the call site — run it after the switch and the *incoming* tab inherits the *outgoing* buffer's dirtiness. Both are now single-sourced through one `active_dirty()` helper, with two source guards: one pinning the capture above the `active_tab` write, one pinning the restore check and the number of live-modify-bit readers at two. Both mutation-verified, and the second only after a first attempt passed against a deleted call because it was matching the identifier in a *comment* inside the function body — it now matches the call form.

Verification of the gesture itself was done by driving the real app rather than by reading it: a temporary probe posted a synthetic down/drag/up triple and asserted the resulting tab order, which caught that a directly-constructed `NSEvent` and a *posted* one do not share a coordinate frame (AppKit rewrites a posted event's location), so the first run reported a plausible-but-wrong drop index. Posting all three and dequeuing the down fixed it and the drag then landed exactly where the arithmetic says. The same probe confirmed pin relocation into the pinned cluster, icon decode at both scales, and — usefully — that the middle-click guard *rejects* a synthetic event, because `mouseEventWithType:` has no button-number parameter and produces button 0. That last one is the honest limit of the automation: the override is proven to be installed and invoked and the guard proven to discriminate, but only a real middle click carries button 2. The drop-index arithmetic is a pure function with its own unit tests, on the same reasoning as `ui_win32`'s `resolve_tab_arm_commit`: the interesting failures are off-by-ones at the half-tab boundary, which a hands-on demo is worst at catching.

**Two blockers and one further hazard were caught by the pre-commit gate**, all three consequences of taking the gesture over from `NSButton` rather than of the reorder logic itself. First, dragging detached the pin and the close from the tab body: they were siblings in the strip container, so only the body moved. Fixed structurally rather than by repositioning three frames per mouse-moved event — they are now **subviews of the body**, so they travel with it for free, and AppKit hit-tests subviews before their parent so both still swallow their own clicks (verified against the live hierarchy: a hit at the pin's coordinates resolves to `CodeppPinView`, at the close's to its `NSButton`, and at the body's to `CodeppTabButton` — `NSButton`'s internal `_NSCoreHostingView` declines).

Second, the tracking loop pumps `NSEventTrackingRunLoopMode` by hand, and GCD's main-queue source is serviced there — so it needed a `DrainFreeze` exactly as much as a modal does, which every other nested loop on this backend already takes. Without it a worker finishing mid-drag could reach `refresh_tab_chrome` → `TabStrip::sync` and tear down the strip under the gesture, or pop an alert while the mouse was still held.

Third, and only visible once the second was being fixed: the commit path resyncs the strip, which sends `removeFromSuperview` to the very button whose `mouseDown:` is still on the stack. The superview holds the only strong reference and Objective-C dispatch does not retain the receiver, so that is a **use-after-free**, not a stale read — and one that would usually not crash, because the freed memory stays mapped and briefly intact. `NSButtonCell`'s own `trackMouse:withFrame:inView:` retains its control view for precisely this reason; a hand-rolled loop that bypasses the cell inherits none of that. `track` therefore decides the gesture *inside* the loop and acts on it *after*, so the last use of `self` is strictly before the mutation, with a mutation-verified source scan pinning it. `PinView::mouseDown:` has the same shape and is sound for the same reason — its model call is its last statement.

The security audit found one Medium that was **pre-existing rather than new, but widened by this milestone**, and it is closed here rather than deferred: none of `ui_cocoa`'s native-invoked entry points had a `catch_unwind` boundary. Every other such boundary in the workspace does — `ui_win32`'s window and dialog procs, `ui_gtk`'s signal handlers, `plugin-host`'s dispatcher, the last of which §6.5 states as a rule — and this backend had simply never adopted it. m3c makes it matter more: `track` is the first entry point here that runs a long-lived nested run loop with model-mutating side effects, and `drawRect:` runs on every paint. `on_sci_notify` is the sharpest case and predates m3c entirely: it is plain `extern "C"`, where a foreign unwind is undefined behaviour outright rather than merely unspecified. All of them now go through one `at_callback_boundary` helper, with `PinView::isFlipped` the single deliberate exception (it returns a literal and AppKit calls it on every layout pass). Worth noting the release profile sets `panic = "abort"`, so this earns its place in dev and test builds — which is exactly where a developer is most likely to trip a panic and least likely to want undefined behaviour as the diagnostic.

**A user testing the drag reported it looked wrong**, and both halves of why are worth recording because neither is about the reorder logic. The dragged tab kept its position in the container's subview array, and subview order *is* paint order — so it was painted *under* every tab that came after it, which reads as merging into its neighbours rather than being picked up. And nothing moved aside, so it overlapped whatever it passed over. Fixed by restacking the dragged button to the top on drag start (`addSubview:positioned:relativeTo:` with `NSWindowAbove`, which is also focus-neutral — measured either side of a drag, the first responder stays the Scintilla content view) and shuffling the other tabs live so exactly one slot is always free beneath it. `GtkNotebook` does both for free, which is why neither was missing on Linux.

That fix pulled in two more things. `track` now holds an owned reference to the button for the whole gesture — `addSubview:positioned:relativeTo:` removes and re-inserts the subview, so without one the container's only reference would be dropped mid-restack — and that reference incidentally makes the receiver outlive the end-of-function resync outright, so the decide-inside/act-outside ordering becomes defence in depth rather than the sole guarantee. It is kept, and still pinned by its source scan. Separately, a `DragGuard` now suppresses `TabStrip::sync` for the span of a drag: `DrainFreeze` covers the worker-wake path, but `on_sci_notify` calls `refresh_tab_chrome` directly and is not gated by it, and a rebuild mid-drag would detach the very views the drag is moving. No notification can fire mid-drag today — every arm that rebuilds the strip needs an edit or a save, and neither is possible with a mouse button held on a tab — so this closes a latent path rather than a live bug. It was closed anyway because the argument for unreachability is about what a *user* can do, which is exactly the premise that stops holding the moment a plugin or a timer can touch a buffer. The audit then found the abnormal-termination case: if the event queue closes without a mouse-up (the app quitting mid-drag), the peers are left in uncommitted positions, and the code returned early on the reasoning that there was nothing to commit — true only when the press never became a drag. It now resyncs.

A second report followed the first and was more informative than it looked: the drag was fine for the *active* tab but every inactive one still showed its neighbours through it. That rules the z-order fix in rather than out — the remaining artifact is transparency. An unselected `AccessoryBar` button draws no background at all, and the dragged tab straddles two slots for the whole gesture, so whatever is beneath shows through; the selected tab has a filled bezel, which is exactly why that one case looked right. A `TabBackdrop` view now fills `windowBackgroundColor` beneath the dragged button, installed **only when the button is unselected** — the backdrop is a subview and so paints after the button's own drawing, which on a selected tab would cover the very bezel that makes it look selected.

It relies on one undocumented detail, named here rather than left implicit: an `AccessoryBar` button renders its title and image through a lazily-created private subview, so a backdrop at index 0 sits behind them. Subview paint order is documented; the label living in a subview is not. If a future macOS moves that drawing back into the button's own `drawRect:`, the backdrop would cover the dragged tab's label — obvious to anyone dragging a tab, but nothing in the suite would fail. The migration is recorded at the call site: drop the subview and fill the background in a `TabButton::drawRect:` override before chaining to `super`. Same discipline as the deprecated `registerNotifyCallback:` note in the shim.

**On how this was verified, and how far that goes.** The strip was rendered in-process to a PNG mid-drag (`cacheDisplayInRect:toBitmapImageRep:`), in both the inactive- and active-tab cases, which is what confirmed the backdrop paints and that the selected case correctly installs none. That path does **not** render AppKit's private hosting view, so button bezels and titles are missing for the non-dragged tabs and the untouched areas come back as blank bitmap rather than the real chrome colour — it shows what Code++'s own views draw, not a faithful screenshot. Enough to answer "is the dragged tab opaque", not enough to substitute for looking at it. Recorded because §8 already carries two retracted conclusions that came from trusting an instrument past its range.

The shuffle arithmetic is pure and unit-tested, including a property test that every drag leaves the remaining tabs on distinct slots with exactly one gap — the invariant that actually determines whether it looks right.

**macOS m3d — the menu tree (landed).** The bar goes from three menus to nine: Search, View, Encoding, Language, Window and `?` join App, File and Edit, with File gaining Close All and a greyed Print. The Notepad++ tree everywhere the platform does not mandate otherwise, per the m1 convention decision — so About, Settings and Quit stay in the application menu and every shortcut is a ⌘ chord.

**Check and radio marks are painted from `validateMenuItem:`, not tracked per item**, which is the one structural difference from `ui_gtk`. It now uses the options form of the same panel, carrying the fields `ui_win32` and `ui_gtk` show: name, version with the 64-bit/32-bit suffix in Win32's own shape, the shared summary line, the home page, the Scintilla and Notepad++ acknowledgements, and the MIT copyright. The icon is the same `assets/code++.png` the other two use, embedded rather than loaded from disk. Keeping AppKit's panel rather than hand-building a window is the m1 convention decision applied where it actually binds — About is one of the three App-menu items macOS mandates — while the *content* is the cross-platform one. The icon key is **omitted** when the PNG will not decode rather than defaulted to something else: the header documents only the absent-key fallback and says nothing about a present-but-wrong-typed value, and an audit rightly refused an earlier comment that asserted AppKit tolerates one.

Second, roughly 80 of the Language menu's ~88 rows live in lettered submenus, so a buffer detected as C++ showed its checkmark only to a user who already thought to open "C". The letter group containing the active language now carries the mark too. It is pushed from the menu's `menuNeedsUpdate:` rather than resolved in `validateMenuItem:` like every other mark in this backend, and the reason is structural rather than stylistic: **AppKit does not validate an item that owns a submenu**, because validation resolves an item's *action* and a submenu item has none. Verified by driving the app — with C++ active the "C" group marks, and switching to Python leaves only "P" marked, so no stale tick survives a language change.

**macOS m3e — the toolbar (landed).** 32 buttons in 10 separator-delimited groups, the same layout and the same `assets/icons/` artwork `ui_win32` blits and `ui_gtk` decodes, so all three bars are button-for-button identical. `NSToolbar` is deliberately not used: it lives in the *titlebar* and owns its own item model, overflow and customisation UI, whereas Code++'s toolbar is a content-area bar above the tab strip. Placement is not something macOS mandates, so the m1 convention decision keeps Notepad++'s. Composed from `NSButton`s in an `NSView`, like the tab strip.

Wired: the file group, clipboard, undo/redo, zoom, and the three view toggles. Greyed: search and print (m4's dialogs), the panel toggles (m4), sync-scroll, monitoring and the macro group. **Greying is an explicit `setEnabled(false)` here, which is *not* how the menu does it** — the menu relies on AppKit's automatic *menu* enabling, where an item whose action has no implementor is greyed for free. There is no equivalent for a control, and the first version of this file assumed there was: driving the app reported all 32 buttons `isEnabled() == true`, i.e. two-thirds of the bar looked live and did nothing on click, which is exactly the dead click listing them greyed is meant to prevent.

The toggles are `PushOnPushOff`, so AppKit has already flipped the button's state by the time the action fires; the handlers therefore *apply* that state rather than inverting the model, which would fight the button and land on the wrong value every other click. Toolbar and View menu cannot drift because every View-setting mutation ends in one `refresh_toolbar_toggles`, and the menu resolves its own marks on open — `ui_gtk` needs a registry of widget handles plus a re-entrancy flag to achieve the same thing.

The pre-commit gate caught one blocker and one thing worse than the blocker. `set_toolbar_hidden` returned `true` rather than the **previous** hidden state, which is the trait's stated contract and what reaches a plugin as `NPPM_HIDETOOLBAR`'s return value — `plugin-host` has a test pinning exactly that. Then, fixing it surfaced that hiding a strip left a blank band: autoresizing masks handle a window *resize*, but a hidden view keeps its frame. Win32 relayouts after its `ShowWindow`; a comment of mine claimed it did not, which was simply wrong. The new `relayout_chrome` recomputes all four bands from scratch, and it is a **method on `CocoaUi` rather than a free function** — every `UiPlatform` method already runs inside a `with_state` borrow, so a nested one is declined and the first version silently never ran at all. Measured either way: the editor's frame did not move on any of four hide/show calls before the fix, and afterwards gains exactly the toolbar's 30 pt, then the tab strip's 26 pt, and restores. That also closes the same gap the tab strip had carried since m3a.

**macOS m4a — Find/Replace and Go To (landed).** m4 is split; this is the first part, and it lights up the whole Search menu bar one entry plus two toolbar buttons. Find/Replace is a modeless `NSPanel` with the `UtilityWindow` style mask — so it floats and does not take main-window status from the editor, which is the closest AppKit has to the tool-window role `ui_win32`'s `WS_POPUP` class plays. Go To is a modal `NSAlert` with a text field in its accessory slot. The shared query field and the three option checkboxes sit above an `NSTabView`, each tab carrying only its own controls, the same split `ui_gtk` uses; the Find-in-Files tab waits for the results dock, since it needs somewhere to put its output, and lands in m4b below. Find-in-Files stays greyed in the menu until then.

An `NSTabView` here is not a contradiction of the rule that rules it out for the tab strip: the objection there is that it owns per-tab *content views* and a Scintilla view must not be owned that way. These tabs own ordinary control panels.

Three findings from the gate, and two of them are the kind that would have shipped looking fine.

**⌘H for Replace was dead on arrival.** macOS mandates "Hide Code++" in the application menu, which is installed first, and `performKeyEquivalent:` stops at the first match — so the shortcut would have appeared beside Replace in the menu and only ever hidden the app. Replace is now ⌥⌘F, which is what macOS editors use. The general problem is that a duplicate key equivalent fails *silently*, so `menu::install` now carries a `debug_assert` that walks the whole bar and refuses two items claiming the same chord; driving the app confirms 28 key equivalents with zero collisions, and that ⌘F and ⌥⌘F differ only in the modifier mask as intended.

**Replace left the chrome stale.** Scintilla emits `SCN_MODIFIED` synchronously from inside the edit, so it re-enters `on_sci_notify` while the `with_state` borrow that issued the replace is still held, and `with_state` correctly declines — exactly the obligation `on_sci_notify`'s own docs state and the reason they say a new caller that forgets leaves the marker stale with no other symptom. "3 replaced" appeared in the panel while the tab's dirty dot and the status bar's length did not move. Every command now refreshes the chrome after its borrow returns. **`ui_gtk` has the identical gap** in its own `do_replace_one` / `do_replace_all`; it is not fixed here because there is no Linux runner on this host, and is tracked in §7.4.

**The query field is seeded from the selection, and that is a chrome sink.** Buffer text is attacker-influenced, and §7.4 catalogues three prior incidents of hostile text reaching chrome unsanitized. The fix is deliberately *not* the substitution every other sink uses: this field's contents are the actual search parameter, so replacing a bidi override with U+FFFD would quietly search for something the user never asked for and report "not found" for text plainly on screen. A display-hostile selection therefore seeds *nothing* and the user can still type the term — the same call `ui_gtk` makes for its Find-in-Files directory field, which is the one place it already reasoned this through. `ui_gtk`'s *query* field has the same unguarded seed and is tracked in §7.4 alongside the refresh gap.

Verified by driving the real app: the panel builds and shows; Count reports "3 matches" on a seeded buffer; Find advances the caret 0 → 11 → 23 including through the menu's repeat path, which uses the shell's remembered query so it works with the panel closed; Replace All reports "3 replaced" and the resulting text is correct; Match case flips a count between 0 and 1. `parse_goto_line` and the seeding rule are pure helpers with unit tests, because their interesting cases are all input shapes — and a modal cannot be driven from `cargo test`. The Go To alert's *construction* was checked instead (message text, two buttons, accessory view identity, initial first responder), `runModal` itself being machinery this backend already exercises in three other places.

**Seven items from hands-on testing, fixed together.** Worth recording as a group because five of the seven are the same shape: AppKit's default is not the cross-platform behaviour, and the default is silent.

* **The editor painted over the status bar.** `SCIScrollView` is a *flipped* view, and on macOS 26 it carries a scroll-edge-effect `NSVisualEffectView` sized 690 pt inside a 548 pt scroll view — so that child extends ~140 pt *below* the editor's frame, and AppKit does not clip subviews to their parent by default. Measured from the view dump, which also shows the horizontal scroller at y=531 of 548, the only reading of which is that the view is flipped. Fixed with `setClipsToBounds` on the Scintilla view, which states the invariant the layout already assumes rather than chasing whichever AppKit-internal subview currently overflows.
* **Selection was system-accent blue rather than the neutral grey the other two backends show.** `ScintillaCocoa::UpdateBaseElements` derives `Element::SelectionBack` from the system selected-text colour; Win32 and GTK install no such base and keep Scintilla's own. Fixed with an explicit `SCI_SETELEMENTCOLOUR`, which is what it takes — the Cocoa value is an element *base*, and only an explicit element colour overrides one. Scoped to exactly the three elements that backend overrides.
* **No visible scrollbar.** macOS defaults to overlay scrollers, which appear only during a wheel or trackpad scroll — so scrolling by keyboard, by dragging a selection or from a plugin left no indication there was more document. Forced to `Legacy` on the editor's scroll view only. This deliberately overrides a system preference: a code editor's scroll position is information, not decoration.
* **The Find panel floated above *other applications*.** `setHidesOnDeactivate(false)` had been called with a comment claiming it was about Escape, which it is not. A utility panel's default is to hide on deactivate, so the call is simply gone. The replacement comment's Escape claim was then *measured* rather than repeated — and in the case that could have broken it, with the query field focused so the first responder is an `NSTextView` with its own Escape handling. It closes.
* **The Replace field overlapped its buttons.** The tab page's inner rect came out 50 pt tall and the field was positioned by measuring down from the top. Now laid out bottom-up, so the rows cannot collide at any page height, with the panel also made taller and a unit test pinning the constants.
* **The About panel's Notepad++ acknowledgement removed** at the user's request. `README.md` keeps its Acknowledgements section, so the credit stands where the project describes itself; this changes only the in-app panel.
* **"Show Tab Bar" / "Show All Tabs" appeared in the View menu.** Not Code++'s: AppKit injects them for any window with tabbing enabled, and they offer a *second*, full-width native tab bar that groups windows. Code++ is single-window by design (§10) and has its own document tab strip, so the items could only ever produce a bar with one entry that had nothing to do with the buffers. `setTabbingMode(Disallowed)` removes them.

**Tab-strip overflow (landed, post-m4a).** Reported by a user: with enough tabs open to exceed the window width there was no way to reach the ones off-screen. A real gap, and one that had not been recorded — the other two backends get overflow *for free from a native control* (`ui_gtk` calls `notebook.set_scrollable(true)`; `ui_win32`'s `SysTabControl32` grows its own spinner), and the Cocoa strip is hand-composed `NSButton`s in a plain `NSView` because `NSTabView` would own per-tab content views and break the single-view rule. Nothing in that laid out an overflow case, so surplus tabs were simply positioned off-view.

Now: a scroll offset, trailing chevron arrows shown only while overflowing, and a reserved lane so the last tab is never stranded under them. Selecting an off-screen tab — from the Window menu, by closing its neighbour, or from a plugin — scrolls it into view. The offset lives in a `thread_local` rather than on `TabStrip`, which is `Clone` and handed out on every drain, so a field would give each copy its own. The drag-reorder arithmetic works in slot space, so every conversion from a button's frame now adds the offset back; the helpers are pure and unit-tested, including that an already-visible tab does not move the strip.

Two bugs were caught before this shipped, and both are worth recording because each was invisible to the test that was supposed to catch it. Driving the app showed the arrows were **inert**: `scroll_into_view` ran on every chrome refresh, so each press moved the offset and the refresh that followed dragged it straight back to the active tab. It is now keyed on the active buffer's *id* changing, so a reorder — which changes the index without changing the buffer — does not count as a switch. Then the pre-commit gate found that **nothing resynced the strip on a window resize**: the container is width-sizable so it tracks the window, but the buttons inside carry no autoresizing mask and are only positioned by `sync`, which runs on tab-list events. Narrowing a window past the overflow point therefore produced no arrows at all — silently reproducing the very bug this work fixes — until some unrelated edit refreshed the chrome. The first verification run had missed it because the probe called `refresh_tab_chrome` itself right after resizing; a `windowDidResize:` delegate now does it.

A follow-up report said the arrows looked wrong — see-through, with the tabs showing under them. Reserving a lane width bounds how far the strip can *scroll*; it does not stop the tabs being *drawn* there, and AppKit does not clip subviews to their parent. The tabs now live in a clipped child view sized to the lane, with the arrows as its siblings — so they sit beside the tabs, which is where the other two backends put them, and nothing can reach under them, a dragged tab included. Verified by hit-testing across the strip rather than from a render, because the in-process capture path does not draw AppKit's private hosting views: the lane owns every point up to its own width and the arrows own the rest, with no overlap.

That hook also exposed a smaller one: `windowDidResize:` fires *synchronously* from `setContentSize`, and its refresh needs `with_state` — so View → Restore Default Window Size, which resized from inside a borrow, had its own refresh declined by the re-entrancy guard and left the strip laid out for the old width. It now takes the window out of the borrow first.

**macOS m4b — the Find-in-Files results dock (landed).** The second part of m4, and the one that unlocks the entry m4a had to leave greyed. A third tab on the Find/Replace panel — directory, filters, its own replacement field, sub-folder and hidden-folder toggles, Browse on an `NSOpenPanel` — plus a results dock along the bottom above the status bar, with a summary header, Cancel, close, a drag-to-resize divider and an `NSTableView` whose rows double-click through to the match. The search *engine* needed no work at all: `codepp_core::fif` and `codepp_shell::fif` are cross-platform, so a backend only builds a `FifRequest`, drains `FifEvent`s on each §5.4 wake, and implements the jump. In-open-buffer Replace-in-Files needed no code here either — `Shell::drain` applies it through the `is_doc_dirty` / `replace_doc_text` hooks this backend already provided.

**The one structural difference from `ui_gtk` is forced rather than chosen, and it is the interesting part.** `NSTableView` is data-source driven: AppKit asks for the row count and for each visible row's view *whenever it lays out*, including synchronously inside `reloadData` and inside a `setFrame:` that resizes the table. Several of those calls originate from code already inside a `with_state` borrow — the drain flushes results, and `relayout_chrome` resizes the dock from a `UiPlatform` method. A data source reaching back through `with_state` would be declined re-entrantly on exactly those paths and would answer *zero rows*, so the dock would blank itself the moment results arrived or the toolbar was toggled. The rows therefore live in a main-thread `thread_local` the data source reads directly. That was verified rather than assumed: driving the app, the table reports its four rows from inside a live borrow, while a nested `with_state` from the same place returns `None` — so the trap is real and the design avoids it.

The value-vs-label split the other two backends make is here too, and was checked adversarially: a file named `invoice\u{202E}fdp.txt` renders in the dock as `invoice<U+FFFD>fdp.txt` while the row's jump target keeps the real path, so a double-click opens the file the row is actually about rather than the one its label spells.

**The pre-commit gate caught one blocker, and it is the same class of bug as m3e's hidden-strip band.** `clamp_dock_height` was applied only where the user drags the divider — but the persisted height outlives the window size that justified it, and a plain resize is handled entirely by autoresizing masks, where the editor is the only flexible view and therefore absorbs the whole delta. Shrinking the window under an open dock starved the editor to zero while the dock kept its height. `ui_win32::layout_children` re-applies its own `clamp_dock_height` on *every* layout for exactly this reason, and `ui_gtk` gets it free from `GtkPaned`; only the drag-time half had been ported. The clamp now lives in the layout path and `windowDidResize:` re-runs it, with two mutation-verified source guards pinning both call sites — the property is unobservable without a real window server, which is what that tool is for. Deliberately *not* written back, matching Win32: growing the window again restores the height the user dragged rather than leaving it stuck at the smallest intermediate size. Measured: a 478 pt dock yields to 402 → 202 → 84 as the window goes 768 → 600 → 400 → 250 with the editor holding its 120 pt floor, and comes back to 478 on restore.

Two smaller things, both found by driving rather than by reading. The dock's header row and its buttons carried no vertical autoresizing mask, so they stayed at their original `y` as the divider made the dock taller — which looks perfectly correct at the opening height and buries the header under the results table once dragged. And a security audit found `url_to_path` had never been gated on `isFileURL()`, unlike its drag-and-drop sibling `dragged_paths`; m4b adds a third caller, so it is closed here rather than inherited again.

**Two user-reported bugs, fixed post-m4b, and one of them is a `Shell`-level behaviour every backend now shares.**

*Save-then-close saved and did not close.* Confirming the Save / Don't Save / Cancel prompt wrote the file and left the tab open. The gate re-read the **cached** `Tab.dirty` to decide whether the save had succeeded, and nothing had cleared it: `save_current_to_disk` calls `ui.mark_saved()` from inside the `with_state` borrow it is holding, so the `SCN_SAVEPOINTREACHED` that follows re-enters `on_sci_notify` with that borrow live and is declined — exactly the obligation `on_sci_notify`'s own docs state, and the third time this backend has been caught by it (the m4a Replace case is the second). The same borrow is why a plain ⌘S left the tab's dirty marker showing unsaved changes for a file already on disk, which is the same bug wearing different clothes; both save paths now refresh the chrome after their borrow returns. The gate itself now reads `active_dirty()` — the live modify bit ORed with `is_unsaved_restore`, so a crash-recovered buffer closes once it has a real copy on disk and not before. **Neither other backend had it**: `ui_gtk` re-reads `SCI_GETMODIFY` at this point and already refreshes after every save, and `ui_win32` decides on the save's `Result` rather than on any dirty bit.

Verified by driving the app, and the mutation is what makes it conclusive: with the chrome refresh reverted, a save leaves `live_dirty=false, cached_dirty=true`, the old gate answers "still dirty → abort" and the new one answers "clean → proceed". A first attempt at the probe proved nothing, because it issued its edit from inside a `with_state` borrow and so suppressed the very notification that sets the cached bit — the reproduction has to type the way a user does.

*Opening a file left the untouched `new 1` behind.* Notepad++ discards the startup scratch buffer when you open a real file into an otherwise-empty workspace; Code++ opened beside it on all three backends. Fixed in `Shell` rather than per-backend, as `Shell::open_file_replacing_scratch`: the existing reuse machinery in `open_file` already retargets a load onto an empty tab, and this widens its gate for one documented case — the lone untitled tab, not dirty, not renamed, not a crash-recovery restore, with the caller confirming the editor is *pristine*. That last fact is the only one the headless shell cannot see, so the UI measures it and passes it in. `open_file` keeps today's behaviour by delegating with `false`, which is what session restore and the plugin dispatcher want.

**Pristine means empty *and* free of undo history, and the redo half of that is load-bearing rather than defensive.** Measured: type one character into the startup buffer and undo it, and Scintilla reports `SCI_GETLENGTH == 0`, `SCI_CANUNDO == 0`, `SCI_CANREDO == 1`. Every clause but the redo one says "untouched", so a check written against length and undo alone would silently discard a buffer the user had been working in. `Tab.text` is not a substitute either — it is refreshed only on load and on save, so for a buffer typed into it still holds the empty string the tab was created with.

The change also closed a latent hole one level down. `apply_load_result`'s error arm removes the tab it created for a failed open, and reusing the scratch made "the removed tab was the only one" newly reachable — a workspace with no tabs at all, where the strip paints from an empty vector while the single Scintilla view still shows an editable document nothing tracks. It re-seeds an untitled buffer now, which also fixes the pre-existing case of a session restoring a single file that has since been deleted. The test that pinned the old zero-tab outcome was written against a `Shell` with no tabs to begin with, which no real UI ever presents.

**The pre-commit gate then found that the re-seed had introduced a leak of its own — and the first fix for that leak was itself wrong, which is the part worth recording.** The error arm decided a tab was disposable with `path.is_none()`, sufficient only while every tab reaching it had been pushed by `open_file` moments earlier and never activated (`Tab::default()` leaves `scintilla_doc` at 0). Reusing the scratch broke that unstated premise: the `new 1` has a real document, bound by `new_untitled`, and `self.tabs.remove` drops the `Tab` and that pointer with it. `ClosedTab` is the *only* channel by which a document pointer ever reaches a backend's `SCI_RELEASEDOCUMENT`, so the document leaked outright — and then, the list now being empty, the re-seed allocated a *second* one plus a fresh buffer id that would silently invalidate any id a plugin had cached.

The obvious repair is to add `&& scintilla_doc == 0`, and a security audit caught that it trades one bug for another. **`scintilla_doc` is not a proxy for "this tab already existed", because `bind_active_view` materialises a document for any active tab lacking one with no `pending_load` gate.** An ordinary fresh tab therefore acquires one as soon as the user clicks back onto it while its load is still running — and `load_npp_session` reaches the same state with no click at all, deterministically, by restoring the recorded-active tab while its load is in flight. Keyed on the document, such a tab would survive its own failed load as a pathless, `untitled_seq`-less phantom in the strip: exactly the `id != 0 ⇒ path is Some` break the arm exists to prevent, reintroduced through a different door.

What ships records the fact instead of inferring it: `open_file` inserts the request id into `loads_onto_existing_tabs` at the moment it retargets onto an existing tab, and the failure arm takes it back out. Mutation-verified in both directions, which is what makes the pair of tests worth having — reverting to `path.is_none()` alone fails the leak test, and reverting to the `scintilla_doc` proxy fails the phantom test. Only the recorded fact passes both. Adding the comment pushed `apply_load_result` past clippy's 100-line gate, so the whole arm moved into `apply_failed_load`.

One case is left open rather than closed: a fresh tab that *was* prematurely bound still leaks its document when its load fails. That predates all of this — it is what the original `path.is_none()` test did too — and closing it needs a document-release channel the `UiPlatform` trait does not have. Tracked in §7.4.

**Three more from hands-on testing, and each turns on something the platform lays out for itself.**

*A long filename ran under the pin and the close button.* Both are **subviews of the tab body** — m3c made them so deliberately, to avoid repositioning three frames per mouse-moved event during a drag — so the body's bounds are the whole 150 pt tab, and that is the width AppKit lays the title out in. Measured, the pin sits at x=116..132 and the close at 132..150 while the title spans 0..150, so a truncated name and a pin end up drawn on top of each other and neither is legible. Narrowing the *button* is not available: AppKit hit-tests a subview only after the point falls inside its superview's bounds, so pushing the two controls outside the body would leave them visible and dead. The label is therefore shortened by hand against a measured budget and drawn leading-aligned rather than centred. The policy — how many characters to drop, where the ellipsis lands, what happens at degenerate sizes — is a pure function with an injected measurer and its own unit tests, because its interesting cases are all input shapes; the cell keeps its `ByTruncatingMiddle` as a backstop.

*The line-number gutter ran a scrollbar's height past the text.* It is an `NSRulerView` (`SCIMarginView`), which means `NSScrollView` lays it out and not Scintilla — and it gets the scroll view's **full** height. The post-m3b scroller repair had corrected the clip view and never touched the ruler, so with a horizontal scroller on screen the gutter painted a line number level with the scrollbar, for a line whose text was not there. Measured: ruler 690 pt inside a clip of 673, scroller occupying 673..690. Trimming the ruler to the clip's height leaves that corner showing the scroll view's own background, which is what the strip should look like beside a scrollbar. Re-asserted in the same idempotent compare-then-set as the clip, on every paint.

**Trimming it is half the fix, and the other half only showed up when a user looked at it.** Scintilla paints the gutter a whole line-row at a time, so a trimmed ruler leaves a partial row that `PaintMargin` still fills in full — and AppKit does not clip a view to its own bounds by default. The gutter therefore drew a few points past its own frame, reported as "spilling onto the area below". `setClipsToBounds` on the ruler closes it, the same one-liner and the same reason as the `setClipsToBounds` already on the Scintilla view. Upstream meets the same geometry from the other side and takes the opposite exit: `drawHashMarksAndLabelsInRect:` deliberately paints the *whole* margin rect when the ruler is taller than the content, with the comment "Legacy scroll bar mode leaves a poorly painted corner" — i.e. it covers the corner rather than vacating it.

**This one needed a real screenshot, and two cheaper instruments gave the wrong answer first.** The frames were exact integers with no overlap, and the in-process `cacheDisplayInRect:` capture showed a clean boundary — both consistent with "nothing is wrong". `screencapture -l<windowNumber>` against the live window showed a 16 × 3 pt patch of margin grey stranded below the ruler's real bottom edge, which is what identified it as over-paint rather than mis-layout. A first fix attempt — invalidating the band the shrinking ruler vacated, on the theory that it was a stale repaint — changed nothing and was removed rather than kept "just in case"; the classification map from the screenshot is what showed the surrounding band was already repainting correctly. That capture-by-window-id path is worth remembering: it is the only instrument on this backend that has been faithful about AppKit's own drawing, where §8 already records two that were not.

*A new empty buffer inherited the previous file's horizontal scroll range.* `scrollWidth` belongs to the **view**, not the document — it is a tracking high-water mark shared by every buffer the one Scintilla view holds, and it never shrinks by itself. `rebind_active_view` was the only place that re-seeded it, which left every other path that swaps a document stale. Measurement turned up a second instance the report had not mentioned: a short file opened after a long one, whose load lands in `Shell::drain` and never goes near the rebind.

**The obvious fix is to seed at the document swap, and the pre-commit gate caught that it is wrong.** `UiPlatform::activate_tab` *is* the swap and looks like the tighter place for it — but `Shell::save_all` binds every titled tab in turn purely so it can read the buffer text, then rebinds the one the user was actually on. Those are bookkeeping swaps, not navigation, and seeding on them resets the horizontal scroll *position* of a buffer the user never left. Measured, and mutation-confirmed against the seed disabled: with a buffer scrolled to x=1500, File → Save All returned it to 0.

What ships checks the bound document once the binding has **settled** — from `refresh_tab_chrome`, which runs after every drain, open, tab switch, close and File → New — and seeds only when the pointer differs from the one it last seeded for. That needs no way to tell the two kinds of swap apart, because a transient swap restores the original document before the check ever runs. A source guard asserts `platform.rs` calls neither helper, which is the specific mistake, with the reasoning at the assertion; mutation-verified.

**Keying on `Tab.id` instead was proposed by the security audit and is wrong here, which took a measurement to establish rather than an argument.** It looks strictly better — this project's own §7.4 rule is to key on ids rather than on pointers or indices, and it would retire the ABA reasoning a raw document pointer needs. But `Shell::open_file` moves `active_tab` at *request* time, before the load has produced a document, so the id changes a step ahead of the binding. Instrumenting both keys side by side: with an id key the seed fires against the **outgoing** document while the incoming tab still reports `scintilla_doc == 0`, and is then *skipped* on the refresh that follows the real bind — so the buffer the user ends up looking at is never seeded at all. It still produced the right width in a straight-line test, because nothing repainted the outgoing document in between, which is exactly what would have made it convincing on inspection.

The audit's other finding was correct and is fixed: the comment justifying the pointer key had the vendored ordering backwards. `Editor::SetDocPointer` releases the outgoing document **before** assigning the incoming one (`Editor.cxx:5451`) and `Document::Release` deletes synchronously at refcount zero — so the safety does not come from Scintilla's ordering at all. It comes from the caller side: an incoming document is always allocated before the call that could free the outgoing one, so the address handed to a bind is never one that bind is about to free. Worth recording because the first reviewer stated the ordering the other way round and the comment was written from that; only reading `Editor.cxx` settled it.

**On how far that last one is verified, because two instruments failed before one worked.** `scrollWidth`, `SCIContentView.frame`, and AppKit's own `documentRect` / `documentVisibleRect` all agree at the clip width afterwards, against 3973 before — so the document exactly fills the viewport and there is nothing to scroll. That is the mechanism, and it is solid. What could *not* be confirmed in process is the pixel: `NSScroller.knobProportion` turns out not to track the document at all here (it reads 0.4755 on an empty startup buffer, where 1.0 is the only correct answer), and `cacheDisplayInRect:` renders the scroller as a uniform block, the same private-drawing limitation m3c already recorded. Worth stating plainly rather than claiming a visual confirmation: Scintilla sets `hasHorizontalScroller` from `horizontalScrollBarVisible && !Wrapping()`, unconditionally true with wrapping off, so the *track* is always present on this backend regardless — the same permanent-bar behaviour §7.4 records for GTK. What this change alters is whether there is anything to scroll.

**macOS m4c — the Document Map (landed).** The right-side miniature with the translucent orange viewport box, and the first thing on this backend to need a **second permanent Scintilla view**. It shares each tab's document through `SCI_SETDOCPOINTER` exactly as the main view does, so no buffer text is duplicated, and like the main view it is created once and never destroyed, removed or reassigned — the discipline §7.4 makes binding here, now pinned by a source scan that counts `scintilla_cocoa_new()` call sites and asserts neither view is ever removed from its superview. `ui_gtk` carries the same guard at the same count; this backend had none until now, because until now the count was one.

Three things are Cocoa-shaped rather than ported. **The overlay is a plain sibling view**, added after the miniature: AppKit paints subviews in array order and hit-tests them in reverse, so a later sibling is both on top and first to the mouse, with whatever it does not paint left transparent — no `GtkOverlay` equivalent needed, and no container type at all. It overrides `isFlipped`, so the y coordinates Scintilla reports for the miniature are used directly rather than mirrored against a height that changes with every window resize. And **the map splits the editor band horizontally**, which the layout had never had to express: `relayout_chrome` computes four stacked bands, and the map is the first thing to take width out of one of them rather than height off the stack.

**Why the overlay owns the mouse is worth stating, because the obvious alternative is a trap the other two backends already document.** `SCI_SETREADONLY` looks like the way to stop the miniature editing the buffer and cannot be: it is a **document** property, so setting it on the miniature freezes the *main* editor the moment they share a document, and setting it on the miniature's throwaway initial document is superseded by the first `SCI_SETDOCPOINTER`. The guarantee has to be that no input reaches the miniature at all. Win32 reaches that from two sides (no `WS_TABSTOP`, plus a subclass proc that eats the mouse) and `ui_gtk` from two more (`set_can_focus(false)` plus a key-press swallow).

**The first version of this milestone implemented only the mouse half, and the pre-commit gate caught it.** The overlay covers the miniature and swallows every click, so the module's own docs claimed the whole guarantee — and the keyboard side was wide open. AppKit has **no per-view equivalent of `set_can_focus(false)`**: `acceptsFirstResponder` is a method on the view, and the view is vendored (`cocoa/ScintillaView.mm:420` returns `YES` unconditionally, and so does `SCIContentView`). Measured on the real app, `selectNextKeyView:` — the exact call AppKit's Tab handling makes — **alternated** between the editor's content view and the miniature's, and five synthetic keystrokes after tabbing in moved the document length 12 189 → 12 194. The user sees nothing, because the miniature is configured with `CARETSTYLE_INVISIBLE`, so there is no insertion point to notice.

The fix is an `NSWindow` subclass overriding `makeFirstResponder:`, which is where Tab-cycling, clicks and programmatic assignment all converge — one guard rather than one per route. Mutation-verified in both directions against the live app: with it, Tab never reaches the miniature and a direct `makeFirstResponder(miniature)` is refused; with it neutered, both succeed again.

**Two instrument failures on the way there, and both produced a confident wrong answer.** The first probe's "is the responder inside the map?" helper took its own `with_state` borrow from *inside* an outer one — declined re-entrantly, so it answered `false` for every input and reported the hazard as unreachable. The rewrite carries a control that types into the main editor first and asserts the length moves, so an instrument that cannot see an edit now fails loudly instead of exonerating the code.

The second is the more useful lesson, because it was in the *fix* rather than in the test. `owns_view` originally read the panel through `with_state` — and `makeFirstResponder:` is reachable from inside an outer borrow, where that read is declined and a decline reads as "not the map", which **allows** the focus the guard exists to refuse. A guard that fails open, on precisely the path it protects. It now reads a `thread_local` holding the panel view, so no borrow is involved; a source scan pins both that the window consults `owns_view` and that `owns_view` never reintroduces `with_state`.

The guard is deliberately **coarse**: it refuses focus to any descendant of the panel, not only to the miniature, so the header's close button and the divider are not keyboard-reachable either. That is the conservative direction — the alternative is enumerating exceptions inside a guard whose failure mode is to let typing into the user's buffer — and it costs nothing the other two backends offer, neither of which gives its Document Map panel keyboard navigation. Narrowing it later means special-casing those two views rather than walking to the panel root. What the coarseness *could* have broken was checked rather than assumed, since a refused first responder is a plausible way to break a control: driving the real app, a posted mouse-down/drag/up on the divider resizes the panel 160 → 218 pt (exactly the 60 pt drag less the 2 pt grab offset), a posted click on the ✕ closes it, and the editor is still focusable afterwards. AppKit's control tracking does not require becoming first responder, which is why this works — but "does not require" is a claim about AppKit, and the measurement is about this window.

**One bug was found by driving the app, and it is the kind that looks correct in the code and in the first screenshot.** A closed panel was given a zero-width frame — harmless-looking, since it is hidden — and its subviews are width-sizable, so they collapsed with it. Autoresizing cannot restore proportions from a zero-width superview, so *reopening* the map came back with its 123 pt header label stretched to the panel's full 160 pt, running straight over the close button. Measured either side: 160 pt before the fix, 123 pt after. A hidden view's frame is unobservable, so the layout now simply leaves it alone while the map is closed.

Two smaller gate findings, both closed. The persisted width was the one path writing the panel's width from a value the process did not compute — `session.xml` is hand-editable and a crash can truncate it — so it is now bounded on the way in; nothing downstream was at risk (the layout clamps before any rectangle is built, and `f64 as i32` saturates), but a nonsense value would otherwise have round-tripped back out on every save and survived every restart. And the wheel direction was asserted in a comment rather than established: it is now a pure, tested function, with the AppKit convention taken from the vendored backend's own sign usage — `ScintillaCocoa::MouseWheel` (`ScintillaCocoa.mm:2528-2537`) preserves `deltaY`'s sign into `dY` and treats `dY > 0.5` as `Message::ZoomIn`, so positive is the upward gesture. Worth noting its *scrolling* branch is empty — the Cocoa backend leaves that to `NSScrollView` — which is exactly why the map has to do it by hand.

Verified by driving the real app rather than by reading it: with a 401-line file open, the map binds to the same document pointer as the editor (`same=true`), reports the same line count, and the viewport rectangle moves from y=0 to y=282 when the editor scrolls to line 200 — confirmed against a real `screencapture` of the live window, where the orange band spans the overlay's full width and sits where the arithmetic says. A hit test at the map's centre resolves to the overlay rather than to the miniature, which is the property the whole edit guard rests on. Session round-trip and restore were driven end to end (`<docmap visible="true" width="160"/>` written at quit, panel open and bound on the next launch), including that both indicators — the View-menu mark and the toolbar toggle — come back pressed, since neither is the source of truth for its own state. The width clamp is a pure function with unit tests, on this project's usual reasoning that the interesting failures are boundaries a hands-on demo is worst at catching.

**§8 re-measured, per the rule this section keeps having to restate.** `phys_footprint` **47.4 MB** against a same-protocol baseline of **47.2 MB** with the milestone stashed — so a second Scintilla view costs ~0.2 MB while it is hidden, which is the expected answer and is recorded because "expected" is not "measured". Cold start 186–226 ms against a baseline of 185–210 ms, indistinguishable at this spread. **But the absolute figure does not reproduce §8's 18.5 MB**, taken after the same `session.xml`-clearing correction and on the same machine; the baseline misses it by the same amount, so this is pre-existing rather than m4c's. Attribution at rest is IOSurface 20.5 MB and `MALLOC_SMALL` 14.4 MB dirty, and the footprint settles from 57 MB to 47 MB over the first eight seconds. Recorded as unexplained rather than guessed at — §8 already carries three retracted conclusions that came from a plausible explanation nobody checked.

**macOS m4d — the workspace tree (landed).** "Folder as Workspace" on the left of the editor band: a lazily-populated `NSOutlineView`, a header with Fold All / Unfold All / Locate Current / close, a resize divider, double-click to open, a context menu, a View-menu entry, a live toolbar toggle, and session round-trip of root, width and open state. The second side panel, so the layout now splits the editor band three ways — the map is asked for its width first and the tree is clamped against what is left, which makes the two deterministic rather than order-dependent.

**The security shape is the point of this panel, and it is inherited rather than rediscovered.** §7.4 records the Win32 tree shipping without it: a file named `invoice\u{202E}fdp.exe` rendered as a `.pdf`, and the context menu's "Run by system" then handed the real `.exe` to `ShellExecuteW`. So the label is sanitized once, at insert, and *nothing* ever derives a path from it — every action reads the node's real `PathBuf` — and `within_root` is re-checked at **click** time rather than at menu-build time, so a re-root between opening a menu and clicking it cannot let an action escape. Verified against a real tree carrying that exact filename: the row renders `invoice<U+FFFD>fdp.exe` while its path keeps the real character.

**The model lives in thread-locals, and that is forced rather than stylistic.** `NSOutlineView` asks for row counts and cell views synchronously inside `reloadData`, `expandItem:` and `setFrame:`, and several of those originate from code already holding a `with_state` borrow — the chrome relayout among them. A data source reaching back through `with_state` would be declined re-entrantly on exactly those paths and answer *zero rows*, blanking the tree the moment the panel was resized. The same trap, and the same answer, as the m4b results dock.

Two smaller structural notes. The context menu is presented from a `rightMouseDown:` override rather than the more obvious `menuForEvent:`, because the latter *returns* the menu and an object-returning override has to declare its retain semantics to objc2, whereas `popUpContextMenu:` needs no return value. And symlink loops are unreachable by construction: `DirEntry::file_type()` reports the link's own type, so a symlinked directory is classified as a leaf and never descended — measured, not assumed.

**The gate's sharpest finding was that Unfold All's ceilings did not actually bound anything.** The walk reads folders in timer batches and stops at [`UNFOLD_MAX_FOLDERS`] or [`UNFOLD_MAX_ROWS`], then reveals the result with one expand at the end — and that expand was `expandItem:expandChildren:YES`, which is the obvious call and is wrong. A recursive expand walks every reachable row and fires `outlineViewItemWillExpand:` for each, and that notification *is* the lazy loader. So every folder the ceiling had just declined to read got a fresh synchronous `read_dir`, recursively, down every remaining branch, with no ceiling in sight — the exact "huge `node_modules`" case the ceilings exist to bound, and worse than having no ceiling at all, because it happens in one unbatched call rather than in yielded ticks.

Measured rather than argued, on a 340-directory tree with the folder ceiling temporarily lowered to 5: the fix populates **20** directories, the recursive reveal populates **all 341**. `expand_populated` now expands only folders already read, leaving the rest collapsed and still lazily expandable by click — which is what the ceilings' own documentation always claimed happened. A source scan bans `expandItem:expandChildren:` outright, mutation-verified.

**`ui_gtk` has the same defect**, and it is tracked in §7.4 rather than fixed here: its walk ends in an unconditional `expand_all()` under a comment asserting every row is already populated — true when the queue drained, false when a ceiling stopped it.

**The gate also found one Medium, and it was mine.** `show_find_in_files_at` — added in this milestone so the tree's "Find in Files…" can target a folder — wrote the raw directory path straight into the Find/Replace panel's directory field, while `open_panel` **in the same file** guards that exact field with a written rationale. That field is *functional*: it becomes the search root, and it drives a bulk Replace-in-Files, so a folder name carrying bidi controls would render reordered into the field a user is about to rewrite a whole tree from. Sanitizing in place is not available — it would corrupt the path — so a display-hostile directory is now refused with a message pointing at Browse…, the same call m4a made for the query field. One function away from the panel that gets it right, which is how this class of bug keeps recurring.

A third blocker was plain dead code: the `Open Folder as Workspace…` handler existed with a doc comment naming its File-menu home, and nothing ever added the menu item — so the feature was reachable only through the View toggle and the toolbar button, neither of which reads as "open a folder". Now wired where Notepad++ and the other two backends put it.

Two informational items were closed rather than deferred. `NEXT_ID` was reset on every re-root, which contradicted the invariant written on its own declaration and made every workspace's root row id 1 — so a stale id left on a context-menu item would have addressed the *new* tree instead of resolving to "gone". Not reachable today, since nothing worker-driven re-roots; the guarantee is free and its absence is invisible, which is the argument for fixing it. And the context menu's `popUpContextMenu:` spins a nested run loop where GCD's main-queue source is serviced — the one such loop on this backend without a `DrainFreeze`, now consistent with the rest.

One thing is recorded rather than changed: a **symlinked file** inside the root passes `within_root` on its own path, and the OS then resolves it when the default application opens it — so "Open with Default Application" can reach a binary whose real location is outside the workspace. That is ordinary Finder and editor behaviour, and resolving links before the check would break the legitimate symlinks that fill real development trees. Not a bypass of the check, since no unchecked path is ever handed to the launcher.

**Two more from the same user's testing, and the second is the one that mattered.**

The header put its four action buttons on the title row. `ui_gtk` was corrected to a second row beneath the title after the same report, and the Cocoa port had copied GTK's *original* layout — the panel is narrow by design, so a title and four buttons sharing a line leaves the title a few characters wide. Now two rows, with only the close button keeping the title's, where a window's close control belongs. A follow-up report asked for the action row to be right-aligned rather than left, so both header rows end at the same edge; it is laid out right-to-left from the trailing edge and therefore *called* in reverse visual order, which needs no button count and so has nothing to keep in sync when a fourth is added.

**Then: Unfold All on this project's own directory froze the whole app for seconds.** Not the panel — the editor and every other tab, which is the worst shape a stall can take. The read phase was correctly batched and visibly counted to 3 682 folders; the *reveal* was not. Measured at 18 s of frozen main thread, because every `expandItem:` recomputes the outline view's row array and the resulting model was 59 946 rows, so the cost is quadratic in the tree.

Two fixes, each measured separately. Wrapping the run in `beginUpdates`/`endUpdates` coalesces the recompute into one and takes it to **97 ms — 185× on its own**. That would have been tolerable at this size and is not a fix, because it still scales: at `UNFOLD_MAX_FOLDERS` the same rate is over half a second. So the reveal is *also* batched onto the timer, and both phases now yield on a **time budget rather than a fixed item count**. A count has to guess at cost and is wrong in both directions — it stalls when a batch turns out expensive (twenty `read_dir`s on a cold cache) and wastes wall-clock when it turns out cheap, because the interval then dominates. Switching the read phase to a deadline cut it from 185 ticks to 23 for the same work.

**Worst main-thread stall now 58 / 71 / 70 ms across three runs, against 18 000 ms.** What remains is not something batching can remove: `endUpdates` performs AppKit's coalesced relayout, which is O(total rows) and runs once per batch, so *more* batching makes the total worse rather than better. Seven reveal batches at ~20–47 ms each is the better trade against one at 97 ms. The time budget bounds the work Code++ controls; the relayout on top of it is the platform's floor. Three source-scan assertions pin the coalescing, the budget and the rescheduling, all mutation-verified.

Two things that figure does **not** say, worth stating so it is not read as more than it is. The budget bounds the `expandItem:` loop, not the `endUpdates` that follows it — so "8 ms budget" is not "every tick is 8 ms". And the measurement is against 59 946 rows, while `UNFOLD_MAX_ROWS` permits 100 000: the worst tick at the ceiling is proportionally larger, on the order of 120 ms. Still one-shot and still bounded — the ceilings cap total work regardless of how hostile the tree is — but a tree half again as large as the one measured will hitch correspondingly more. If that proves too much in practice, the lever is the ceiling, not the batching.

**And before that it shipped blank, which no part of the gate could have caught.** A user reported that opening a folder gave an empty rectangle where the panel should be. The cause was one missing line: `content.addSubview(&workspace.container)`. The panel was constructed, stored on the state, and laid out by `relayout_chrome` on every pass — it was simply never parented, so it never drew.

Worth recording exactly why everything passed. The build succeeds, because the panel *is* used. Clippy sees no unused value. A diff cannot show a line that was never written, so both reviewers read past it. And — the part that matters — **a detached `NSView` answers every question a probe thinks to ask**: it keeps its frame, reports `isHidden == false`, hands out its subviews, and will even let AppKit construct cell views for its outline view on demand. My own verification checked the model, the row count, the labels, the paths, the layout arithmetic and the session round-trip, and every one of them was correct. The single question that distinguishes attached from detached is `superview()`, and nothing asked it.

The immediate lesson is narrower than "test more": for a *visual* feature, the only instrument that would have failed is a screenshot, and DESIGN.md already records `screencapture -l<windowNumber>` as the one faithful one on this backend. It was not used here because the numbers all agreed. The guard that now exists — `every_panel_is_added_to_the_content_view` — derives its list from `build_content`'s **return tuple** rather than a hard-coded set, so a future panel is covered the moment it is returned; a hard-coded list would need maintaining by exactly the person who just forgot the `addSubview`. Mutation-verified against removing either side panel's line.

**One of the milestone's own guards was fake, and only the mutation test caught it.** The source scan asserted that `context_command` contains `within_root(` — and deleting its early-return gate outright still passed, because a *different* arm of the same function happens to call it too. A guard satisfied by a different call than the one it is guarding is not a guard. It matches the exact gate form now, and all three mutations kill it. The same shape as the m3c guard that matched its own comment, which suggests the rule worth stating is that a source scan must match the *construct*, not the identifier.

**macOS m4e — User Defined Languages (landed).** Phase 4.6 parity: a UDL buffer is now styled on this backend, and there is a way to pick one. Three pieces, all close ports of `ui_gtk::udl` — `apply_lang` routes a UDL id to `SCLEX_CONTAINER` with the UDL's own palette instead of the Lexilla theme table, `on_style_needed` answers the resulting `SCN_STYLENEEDED` by walking the compiled rules, and `resolve_lang_label` puts the UDL's own `<UserLang name>` in the status bar where "Normal Text" used to sit. The registry is reached through a raw `*const UdlRegistry` captured in `CocoaUiState::split`, not through `with_state`, for the reason the other two backends already document: `apply_lang` runs inside a live borrow, a nested one is declined, and a decline here reads as "not a UDL" and silently applies the wrong styling.

**The menu half is Win32 parity rather than GTK parity, and that is forced by the phase rule.** UDL languages live in a dynamic id space above the built-in constants and are *not* in `LANG_TABLE`, so nothing detects them by extension — the only way to apply one is to pick it. `ui_gtk` ships the "User-Defined language" submenu (Define your language…, Open folder, the N++ collection link) but never enumerates `registry.entries()`, so a loaded UDL cannot be selected there at all; its styling path is reachable only from a restored `tab.lang`. Cocoa gets both: the submenu, and the loaded UDLs flat at the top level below it, which is where Notepad++ puts them. The rows are rebuilt from `menuNeedsUpdate:` rather than at construction because **`build_language_menu` runs before `Shell::new`** — there is no registry to read when the menu is built. The fixed prefix is *captured* at build time rather than hardcoded, because it is ~90 items whose count depends on how `LANG_TABLE`'s labels happen to group into letters, and a stale constant would make the rebuild eat built-in rows.

**One bug was introduced by this milestone and caught by driving the app.** `mark_language_letter_groups` marks the lettered submenu holding the active language by matching child tags — and a menu item's tag defaults to 0, which is `L_TEXT`'s own id. The new "User-Defined language" submenu's three children carry no tag, so the submenu came up ticked for every buffer whose language is Normal Text, i.e. every untitled one. Measured rather than inferred: with the probe reporting `active_lang=Some(0)`, the submenu's state read 1. The fix matches on the **selector** as well as the tag, which states the actual intent ("the group holding the active language row") and stays correct if another non-language submenu is ever added.

**The obvious performance worry was measured and refuted.** Each `SCI_SETSTYLING` fires a re-entrant `SCN_MODIFIED`, and `on_style_needed` must drop its borrow before painting — so unlike the initial paint (which runs inside `apply_lang`'s borrow and whose notifications are therefore declined), those *are* processed, each one driving a full status-bar and Document Map refresh. Driving real edits from outside a borrow: an insert produces 3 `SCN_MODIFIED` — Scintilla's own — and the styling pass that follows produces **zero** and costs 0.01–0.06 ms. Honest scope: that is a 237-byte file, so it says the fan-out is not per-token, not that a large UDL buffer types inside the §8 budget; `paint_style_needed` is line-aligned and capped at ~64 KiB, so the per-pass cost is bounded by construction.

Verified by driving the real app rather than by reading it: a `.md` file restored with the preinstalled Markdown UDL renders headings, emphasis markers, links, inline code and fenced blocks in Edditoria's palette, with "Markdown (preinstalled)" in the status bar; the Language menu grows 26 → 28 items with a separator and the UDL row at tag 1024, and a second update leaves it at 28 rather than accumulating; `validateMenuItem:` marks that row when it is active; switching to Rust marks the "R" group and only it. Four source-scan guards cover what a runtime test cannot see here — the selector-matched mark, the rebuild-before-mark ordering, the `SCN_STYLENEEDED` routing, and the borrow-drop before the paint — all mutation-verified.

**macOS m4f — Recent Files and Preferences (landed).** Preferences was the listed item; Recent Files came with it because the pane has nothing else to configure. `ui_cocoa` had no recent-files region at all — the File menu ended at Print — so a settings dialog on its own would have demoed as "change a value and observe nothing", which the §7.1 phase rule does not accept. The Shell side was already cross-platform (`visible_recent_files`, `take_recent_file_at`, `pop_last_recent_file`, `take_all_recent_files`, `clear_recent_files`, and `RecentFilesHistoryConfig::display_path` for the three display modes), so this is menu and dialog work only.

**The one structural difference from the other two backends is forced, and the measurement is the interesting part.** `ui_gtk` and Win32 build the whole region dynamically — numbered list plus Restore Recent Closed File / Open All / Empty — and nest all of it under one "Recent Files" popup when the In-Submenu preference is on. On Cocoa the three commands are **static** and only the numbered list is spliced in on open, because **AppKit does not call `menuNeedsUpdate:` when it searches for a key equivalent**. `NSMenuDelegate`'s documentation says it does. Measured with a control: with the region populated, a synthetic ⇧⌘T resolves and opens a file; with it unpopulated the same event resolves to nothing on `NSMenu`'s own `performKeyEquivalent:`, on `NSApp::sendEvent`, and when posted to the queue. So a shortcut on a delegate-built item is dead until the user happens to open the File menu once — the exact shape of silently-half-working this backend keeps having to fix. The documented alternative, `menuHasKeyEquivalent:forEvent:target:action:`, is worse: it *replaces* AppKit's own search for every menu sharing the delegate, so answering on behalf of the Window menu would kill ⌘M as a side effect. The cost is three rows that stay flat when Notepad++ would nest them.

**That control is what makes the finding usable, and it was needed.** The first run reported the shortcut dead in *both* cases, populated and not — because a key equivalent is matched against `charactersIgnoringModifiers`, and an uppercase equivalent wants an uppercase character there. The synthetic event carried `"t"`. Until that was fixed the probe was measuring nothing at all, which is the third instrument failure recorded on this backend and the second in two milestones.

Preferences itself is an `NSAlert` with an accessory view rather than a window: the Win32 dialog is a category-list + panel design, and with one category that is a lot of chrome around four controls — `ui_gtk` reaches the same conclusion with a plain framed modal. It also reuses a modal path this backend already exercises, where a fresh `NSWindow` would need its own `setReleasedWhenClosed(false)` care. It lives in the **application menu** as "Settings…" with ⌘,, which is where macOS mandates it, per the m1 convention decision. Out-of-range and unparseable numbers keep the previous value rather than being clamped: clamping a typo silently applies a number the user never chose, and `Shell::set_preferences` clamps again anyway.

Verified by driving the real app. All four File-menu shapes: the flat numbered list with tags 0..n; one "Recent Files" submenu with In-Submenu on; the whole tail hidden with the feature off, so the menu ends at Print rather than a dangling separator; and the three commands alone with an empty list, where `validateMenuItem:` returns false for each. A second rebuild leaves the item count unchanged (23 → 23), so the splice is idempotent rather than cumulative. ⇧⌘T resolves with the menu never opened where it previously resolved on no path at all. The dialog round-trips every field exactly — the negative-sense checkbox included — and rejects `999` and `abc` back to the stored values. Two source guards, both mutation-verified: the shortcut is on the static tail and not in the rebuild, and the labels are sanitized. One earlier reading was wrong and is worth recording: a blurry screenshot suggested "In Submenu" had joined the radio group; at full resolution both checkboxes are rounded squares and only the three modes are circles, and a functional test (set it, click a radio, re-read) had already said the same.

**The security audit found one Medium, and it turns on the one way these rows differ from every other dynamic menu on this backend.** Their tag is a list **index**, where the Window menu's is a `Tab.id` and the Language menu's a language id. All three "leave the rows alone" when the state read is declined — correct for a stable key, which resolves to "gone", and wrong for an index, which `open_recent_at` resolves against the *live* list at click time. A row left behind across a list change could therefore open a file other than the one it names. Bounded (only paths already in the trusted list are reachable, and `take_recent_file_at` bounds-checks) but a label that lies about what it will open is exactly the value-vs-label failure this project keeps closing. The removal now happens *before* the read, so a declined rebuild leaves no rows rather than stale ones; the ordering is invisible at the call site — both orders compile and both look right — so it is pinned by a mutation-verified guard.

**The code review's second finding is worth recording because the reviewer was wrong and the measurement is what settled it.** The three display-mode radio buttons carry a shared action selector purely so AppKit groups them; the review read that as dead wiring, on the reasonable grounds that no target is set and AppKit's headers document the grouping mechanism nowhere — concluding that a shared superview alone is what groups radio buttons. Tested directly: three radio buttons in one superview, one pre-selected, then a click on another. With the action they end `[0, 0, 1]`; without it, `[1, 0, 1]`. The superview is not sufficient, so removing the action as dead would have let the dialog hold two modes at once, with `read_back` then resolving by precedence rather than by what the user sees selected. The comment now carries the measurement rather than the claim.

Also closed, one level down: `Shell::clear_recent_files` was the only one of the four recent-files mutators without an `is_active()` gate, while `pop_last_recent_file`'s own doc asserts that *every* recent-files mutation entry point carries one. Unreachable through the UI and it changes no behaviour — `set_preferences` clears through `recent_files.clear()` directly, not through here — so this makes a stated invariant true rather than fixing a bug.

**macOS m4g — the Style Configurator (landed).** The last settings dialog: the Default Style — foreground, background, font family, size, bold/italic/underline — plus window transparency, in the application menu beside Settings…, which is where "Settings → Style Configurator" maps on this platform. An `NSAlert` with an accessory view, like Preferences, and **no live preview**, matching both other backends: nothing reaches the editor until Save & Close. The data path was already cross-platform (`Shell::set_styles`, then `apply_default_style` followed by `apply_lang`), and transparency was already wired here as `NSWindow.alphaValue` in m2, so the slider does real work rather than standing in for it.

The theme / language / style popups are parity chrome and are *disabled* rather than merely single-item, so they read as fixed rather than as controls that failed to populate. `ui_gtk` renders the style scope as a one-row list to match Win32's list box; three popups is the same information in the shape macOS uses for a fixed choice, and it keeps the accessory view short enough to sit in an alert.

Two things are guarded because they fail quietly. `apply_default_style` ends in `SCI_STYLECLEARALL`, which propagates the default over every style index and wipes the lexer's colours — so `apply_lang` has to follow it, or the buffer comes back from the dialog rendered flat until something else happens to re-lex. And a picked colour is converted to sRGB before its components are read: `NSColorWell` returns whatever space the picker produced, catalog and pattern colours included, and `redComponent` *raises an Objective-C exception* for those — which crossing the FFI boundary is undefined behaviour rather than a panic `at_callback_boundary` could catch. Both are source scans matching the call form rather than the identifier, and both are mutation-verified; the first needed the mutation applied as a genuine reorder, since a plain line swap moves a use above its own binding and merely fails to compile.

One layout defect was caught by measuring rather than by looking: the three style checkboxes were each sized to the *remaining* row width, so their frames overlapped two-deep. Clicks resolved correctly anyway — AppKit hit-tests subviews in reverse add order — which is exactly the kind of accident not to build on. They now carry explicit widths.

Verified by driving the real app. The dialog builds with no overlapping rows and its stored values seeded (`Courier New`, 10, black on white, 80% opacity unchecked); the font popup carries all 183 installed families with the stored face selected. A full round-trip through `read_styles` — Menlo, 18, all three flags, red on blue, transparency at 60% — reads back exactly, `400` clamps to 72 and `junk` falls back to the previous 10. Applied for real, Scintilla reports `fore=0x0000ff back=0xff0000` (its BGR order, so red on blue) at size 18 with bold and italic set — underline has no `SCI_STYLEGET*` counterpart queried here, so it is confirmed through the round-trip rather than at the editor — and the window sits at alpha 0.6. The font-list and size helpers are pure with unit tests — including a stored face that is *not* installed, which must be listed and kept rather than silently rewritten the first time the user touches any other control.

**The gate found the dialog was half-useless, and that finding came out of an informational note rather than a blocker.** `ui_cocoa::apply_startup_styles` called `apply_predefined_styles` directly where `ui_gtk` calls `apply_default_style` — which itself calls the predefined styles, after its own `SCI_STYLECLEARALL`. So the margins and brace styles were applied and the *user's saved scheme was discarded* on every launch. Until m4g there was no way to save a scheme on this backend, so the omission had nothing to lose; with the Style Configurator it would have meant every setting silently reverting on relaunch — the dialog appearing to work and forgetting. Measured both ways with a seeded `styles.xml`: without the fix, Scintilla reports `fore=0x000000 back=0xffffff size=11` and the window `alpha=1` — its own defaults; with it, `fore=0x00aa00 back=0x101010 size=16` and `alpha=0.7`, which is what was stored.

**One Medium, and it is the fourth instance of a pattern this document keeps recording.** A font face arrives from `styles.xml` — an ordinary file a user can be handed — and went into the popup as an unsanitized `NSMenuItem` title. Sanitizing in place is not available, because the title was *also* the value read back: a hostile name would have round-tripped as its U+FFFD form and quietly rewritten the user's stored font the first time they touched any other control. So the popup carries sanitized titles and a side table of real faces read back by index, the same value-vs-label split the workspace tree and the results dock use. Verified against a face named `Ev\u{202E}lif.ttf`: the popup shows `Ev<U+FFFD>lif.ttf` while `read_styles` returns the real name. **`ui_gtk::style_config` has the identical gap** at its `combo.append_text(current)` and is tracked in §7.4.

Two informational items are recorded rather than fixed. `apply_default_style` clamps transparency to `0..=100` on all three backends while `Transparency::percent` documents a 20% floor, so a hand-edited `styles.xml` with `percent="0"` yields an invisible window — reachable on macOS only since this commit, because the startup path now applies it. And the dialog's own slider cannot produce such a value. Both belong with the cross-platform sweep rather than a macOS-only clamp that would leave the three backends disagreeing; §7.4 carries them.

**macOS m4h — printing (landed).** The last m4 part, and the last greyed item in the File menu on any backend. ⌘P and the toolbar's Print button now run a real `NSPrintOperation` over Scintilla's `SCI_FORMATRANGEFULL`, with the same settings the other two backends use — colours kept but a default-coloured background forced to white, no magnification, word wrap on so long lines are not clipped at the margin.

**The `hdc` field is not an `HDC`, and on Cocoa it is a `CGContextRef`.** `Sci_RangeToFormatFull.hdc` is whatever the platform layer treats as a `SurfaceID`, and `SurfaceImpl::Init(SurfaceID sid, …)` casts it straight to a `CGContextRef` (`cocoa/PlatCocoa.mm:464`) — so the print operation's own context goes in unchanged, exactly as `ui_gtk` passes a `cairo_t *`.

**The print view is flipped, and that is required rather than stylistic.** `Sci_Rectangle` has `top < bottom` with y increasing downward, and Scintilla's Cocoa surface is written against `SCIContentView`, which answers `isFlipped` YES (`cocoa/ScintillaView.mm:395`) and hands its context straight to `ScintillaCocoa::Draw`. An unflipped view prints every page upside down — something no unit test can see and that costs paper to discover, so it is pinned by a source scan.

The one structural difference from `ui_gtk` is where the pagination runs. GTK paginates in `begin-print`, against the print context, which is valid there. AppKit establishes no graphics context before `knowsPageRange:` — and the page count is needed *earlier* still, because the classic paginated-view model sizes the view at `pages × page height` before the operation exists. So the measuring pass runs against a scratch `NSBitmapImageRep` context: Scintilla's measurement is CoreText layout, which does not depend on where the pixels would land, and the page geometry comes from the rectangle rather than from the context.

Verified by printing to PDF, which is the only way to check the coordinate convention and the content without a printer. A 180-line Rust file produces four pages: page 1 headed `print-demo.rs` / `Page 1` with a hairline rule, syntax highlighting preserved on white, line-number margin intact, right way up; page 4 headed `Page 4` and ending at line 180, with the page starts contiguous (page 1 ends at 47, page 4 begins at 142). An empty untitled buffer produces exactly one page carrying its header and an empty line-number gutter, which is what `paginate`'s always-at-least-one-page clause is for. `paginate` and `page_for_rect` are pure with unit tests — including a non-advancing measurer, which without its guard is an infinite loop on the UI thread, and the half-page boundary that decides which page a draw rectangle belongs to.

**The review found the page geometry was taken from the paper rather than from what the printer can actually mark**, which both other backends get right — `GtkPrintContext` already excludes the non-printable area and `ui_win32` uses `HORZRES`/`VERTRES`. Measured on this machine: a 595×842 A4 sheet whose printable band is 559×783 at (18, 41), so 18 pt in from the left and 18 pt down from the top. The header's 10 pt baseline was *outside* that band — it survived every PDF render, where there is no hardware margin, and a real printer would have clipped it. Everything is now placed inside the band, and the flip from `imageablePageBounds`' bottom-left origin is a pure function with tests, because a coordinate flip is exactly the kind of arithmetic that looks right and prints wrong. The same 180-line file now paginates to five pages rather than four, which is the fix visible in the output: the text column is genuinely shorter than the sheet.

The audit found the module's own "one job at a time" invariant was asserted rather than enforced. `runOperation` spins a modal loop that still services the GCD main-queue source, so a second `show()` dispatched into that window would overwrite `JOB` and clear it on *its* way out, leaving the outer operation to render its remaining pages against `None` — blank paper, nothing reported. Unreachable from the menu today, and reachable the moment `dispatch_npp_menu_command` is wired here, which §7.5 still lists as outstanding. Now an explicit guard; measured that two sequential prints still produce four pages each and the job clears, so it refuses only genuine re-entry.

Worth recording that the empty-page check *first* looked like a bug: a cropped render showed a blank header band, and the header turned out to be present in the full page — `sips --cropOffset` does not crop from the origin the way the invocation implied. The fourth instrument failure recorded on this backend, and the same shape as the others: the measurement was wrong, not the code.

**A user found that the print *preview* came up blank — 19 pages counted, every one empty — and the reason is worth recording because three separate verifications had passed over it.**

During a preview AppKit makes a private `NSPrintPreviewGraphicsContext` current, and that class implements `CGContext` by **forwarding** rather than by declaring it. `respondsToSelector:` therefore answers YES and the message send works, while `class_getInstanceMethod` finds nothing — and objc2's generated accessor consults exactly that under `debug_assertions`, panicking with *"invalid message send … method not found"* before the message is ever sent. `at_callback_boundary` catches the panic, so the page draws nothing; pagination is unaffected because it measures against a bitmap context that has a real `CGContext`, which is why the count stayed right while the content vanished.

**Release builds skip that verification and print correctly.** So the PDF check, the release-build panel check and the paper output were all clean, and the failure existed only in `cargo run` — the workflow DEVELOPMENT.md §4.5 documents for development. The send is now made directly, guarded by `respondsToSelector:` so a context that genuinely has nothing to give is declined rather than sent to blindly. Verified in a debug build against the reported file: zero panics, pages drawing in ~2 ms, preview populated.

The audit corrected the framing on the one part that looked risky. The fix sends the message through a transmuted `objc_msgSend`, so it no longer holds objc2's `Retained<CGContext>` — and that appeared to give up a lifetime guarantee. It did not: `Retained::as_ptr(&x.CGContext())` drops its temporary `Retained` at the end of that statement, so the extra retain was already gone before the pointer was used. `CGContext` is a Get-Rule property and the lifetime has always rested on the owning `NSGraphicsContext` binding. That contract is now written on the function and guarded against the one refactor that would break it — passing a temporary.

Worth stating what this says about the earlier verification. Printing to PDF was the right instrument for the coordinate convention and the content, and it could not have caught this: the PDF path runs through a real `CGContext`, and the preview through a forwarding one. "It prints correctly" and "the preview is correct" turned out to be different claims exercising different AppKit machinery, and only the first had been checked.

**macOS m5 — the plugin host (landed).** The last Phase 5 milestone on this backend, and the one the original plan deferred with a real question attached: *what does plugin support mean on macOS?* The answer turns out to be the one Linux already gives. Binary compatibility is Windows-only by design (§6.1); everywhere else the promise is a **source-compatible recompile**, and `codepp-plugin-sdk` already delivers it — off Windows its `SendMessageW` forwards to a host callback the host installs by `dlsym` at load time, so a plugin needs no OS message pump and no Scintilla of its own. macOS therefore needed no new ABI thinking, only the three AppKit-shaped pieces `ui_gtk::plugin` supplies for GTK: the routing bridge, the Plugins menu, and notification delivery.

**The four in-tree plugins now build on all three platforms.** Their `mod imp` gates read `any(windows, linux)` for no reason that survived inspection — the SDK's non-Windows arm is fully platform-neutral and `cppexport`, the only one that ever wanted an OS dialog or the clipboard, already asks the host for both through the `CODEPPM_EXPORTSAVEDIALOG` / `CODEPPM_SETCLIPBOARD` extension messages. Widening the gates and `BUNDLED_PLUGINS` together was the whole change. The two live in different crates with nothing connecting them, and a mismatch is silent in the worst direction — staging a plugin whose gate excludes the target copies an *empty* cdylib into the user's plugins folder, where it fails to load and shows up in the Plugin Manager as broken — so `bundled_plugins_match_the_imp_gates` now reads each `imp.rs`'s gate attribute and pins the two together.

**Routing is by handle identity, and that is the security-relevant part.** `SCI_*` and `NPPM_*` message numbers overlap, so the number cannot say where a message belongs; only the handle can. A dedicated sentinel's *address* is this backend's npp handle and routes to the shared dispatcher, the one legitimate `ScintillaView*` routes to Scintilla, and **every other pointer is refused**. Win32 gets that for free — `SendMessage` to an unknown `HWND` returns 0 without dereferencing — whereas `scintilla_cocoa_send_message` casts its argument and messages it, so forwarding an unvalidated pointer would turn a plugin bug into a wild `objc_msgSend`. The identity check reads an atomic rather than going through `with_state`, and the direction of that failure is why: a plugin can send `SCI_*` from inside a `beNotified` that already holds the borrow, where a `with_state` read would be declined — and a decline here reads as "not our view" and would **refuse a legitimate message**.

`NPPM_GETMENUHANDLE` degrades to NULL, matching `ui_gtk`. An `NSMenu*` is not an `HMENU`, and a plugin that took one would have to call AppKit on it — outside what a source-compatible recompile promises.

**The Plugin Manager's checkbox carries the registry index, not the row index, and the two are demonstrably different.** `installed_plugins` returns rows sorted by display label while the index is discovery order: measured on the real app, row 0 is "Converter" at registry index 1 and row 2 is "Export" at index 0. A row-index key was then driven to confirm the consequence rather than argued about — clicking Converter's checkbox disabled **Export**. The code's first comment claimed the two "happen to be equal today"; it was simply false, and the mutation is what established that.

**Verified by driving the real app rather than by reading it**, in one pass over the whole path. Four plugins discovered at startup with **zero loaded** — DESIGN.md §8's lazy-load constraint, observed rather than assumed — and all four loaded on the first Plugins-menu open, each reporting its own `getName()`. Their 28 menu items are built from real `FuncItem` arrays with null-`p_func` entries rendering as separators. `example_hello`'s command inserts "Hello from plugin", which proves **both** directions of the bridge in one shot: the plugin's `NPPM_GETCURRENTSCINTILLA` came back with the view handle, and its `SCI_INSERTTEXT` to that handle reached Scintilla. `cppmimetools` Base64-encodes a selection to `aGVsbG8=` through the `SCI_SETTARGETRANGE`/`SCI_REPLACETARGET` round trip. `cppexport`'s "Copy HTML to Clipboard" puts 322 bytes of HTML *and* a plain-text fallback on the pasteboard in one offer. A bogus handle returns 0. The Plugin Manager modal was driven with a GCD main-queue block — which is serviced inside a modal run loop, the same premise `DrainFreeze` rests on — and reports its four rows, three columns and checkbox states from inside the live alert, with a real `performClick` on row 0.

**On how far that last one is verified.** `screencapture -l<windowNumber>` — the one instrument this document records as faithful about AppKit's own drawing — was **unavailable this session**: the capture is refused with *"could not create image from window"* for want of Screen Recording permission, both from inside the process and from the shell beside it. So the manager's *appearance* is unconfirmed. What is confirmed is the property m4d's blank-panel incident says to ask about, and it was asked directly: the accessory view's superview chain resolves through the stack view to the alert's own content view, so the detached-view failure mode — where every question a probe thinks to ask is answered correctly by a view that simply never draws — is excluded rather than assumed. Column widths and label truncation are not.

**Notification delivery was mutation-verified, because the straightforward reading of it proved nothing.** The first probe took the pending count before and after a drain and read 0 both times — but `take_notifications` *consumes*, so the "before" read emptied the queue and the "after" read was measuring its own side effect. Rewritten to read once, and run against the delivery call removed: 0 pending with it, 1 without.

**One of this milestone's own guards was fake, and only the mutation caught it.** The lazy-load guard asserted that `run`'s body does not mention `ensure_plugins_loaded` — and a mutation that moved the load one helper function away passed it cleanly. It now pins the *number of call sites in the whole crate* at one and asserts which function owns it, so any new path to the loader is a second call site wherever it is hidden. Both mutations kill it. The same shape as the m3c guard that matched its own comment and the m4d guard satisfied by a different call: **a source scan must match the construct, not the identifier.**

Two other mutations printed nothing and so proved nothing, both because they did not compile — deleting an `else if` condition left two `else` blocks, and a `Default::default()` for `NppData` does not exist. Redone in forms that build. Recorded because a mutation that fails to compile looks exactly like one the guard failed to catch.

**§8 re-measured against the milestone's own stashed baseline**, per the rule this document keeps having to restate. `phys_footprint` **19.4–19.6 MB** against a baseline of **19.4–19.5 MB**, and cold start **153–253 ms** against **154–247 ms** — indistinguishable at this spread, which is the expected answer for four `stat` pairs and a directory read, and is recorded because "expected" is not "measured". **What this milestone does not do**, stated so it is not read as more than it is. Plugin *shortcuts* are not wired — a `FuncItem`'s `ShortcutKey` is ignored, on this backend and on GTK, so DESIGN.md §6.4's "fires a hotkey owned by the plugin" trigger does not exist on either. ### 7.4 Phase 5 polish items deferred from earlier phases

These are not blockers for the phase that surfaced them, but get addressed in Phase 5 as part of the cross-platform bring-up.

- **Migrate `ui_win32` modal/modeless dialogs from custom `WS_POPUP` classes to standard `#32770` dialog templates.** The Goto and Find/Replace dialogs currently use `CreateWindowExW` with our own registered class. Win11 paints the client area of `WS_POPUP | WS_CAPTION` windows through DWM/UxTheme, outside the `WM_ERASEBKGND` message path entirely — so `WNDCLASSEX.hbrBackground` is silently overridden and our chrome ends up at a slightly different shade than what the system paints. The standard dialog class (`#32770`, instantiated via `DialogBoxIndirectParamW` / `CreateDialogIndirectParamW` with a `DLGTEMPLATEEX` in memory) is the only window class Microsoft retrofitted with cooperative themed-background logic; that's the path Notepad++ uses, and it's why N++'s dialog chrome blends seamlessly. Migrating means a different dispatch model (dialog procs return `BOOL`, use `EndDialog` instead of `DestroyWindow`, etc.) and constructing in-memory `DLGTEMPLATE` byte streams — meaningful work but mechanical. Worth doing in Phase 5 alongside the `ui_gtk`/`ui_cocoa` brings-up because Linux/macOS will need their own dialog primitives anyway, so this is a natural moment to redesign the cross-platform dialog abstraction.

- **~~Replace in Files: handle open files like Notepad++ does.~~ Done for clean tabs (Phase 5); dirty tabs still declined.** The orchestrator used to skip every file the user had open, so a Replace in Files silently did nothing to them. It now hands the replacement it computed to `Shell::drain`, which applies it to the tab's Scintilla buffer — the user keeps undo, the file watcher stays silent, and nothing is written underneath them. Living in `drain` rather than in each backend's results dock means both platforms get it with no UI wiring, and it is testable without one: the end-to-end test runs a real worker pool over real files and asserts the closed file is rewritten on disk while the open one is not and its buffer receives the edit instead.

  **A tab with unsaved edits is still declined**, and that is deliberate rather than unfinished. The worker computes its replacement from the bytes *on disk*, which are not what the user is looking at in a dirty buffer, so applying it would discard their work. Closing that case means re-searching the buffer itself, and the two searches do not use the same engine: find-in-files compiles to the `regex` crate because it runs off the UI thread, while an in-editor search goes through Scintilla's C++11 engine, and the dialects disagree on lookarounds, backreferences and more. Re-searching would risk replacing a different set of matches than the results dock just reported for that file. Resolving it properly means either accepting that divergence explicitly, or moving find-in-files onto Scintilla's engine — which would mean running searches on the UI thread, against DESIGN.md §5.4. Worth deciding rather than drifting into.

  Also outstanding, and small: the counts are reported through `FifEvent::ReplacedInOpenBuffer` but no backend surfaces them yet. They belong on the completion toast alongside the existing "scanned N files" summary.

- **Synchronous plugin notification delivery for `NPPN_FILEBEFORECLOSE` (and friends).** Code++ pushes notifications onto `Shell.pending_notifications` and the UI delivers them to plugins after the current `&mut Shell` borrow ends. That model is right for most events (FILECLOSED, BUFFERACTIVATED, LANGCHANGED, …), but Notepad++ delivers `NPPN_FILEBEFORECLOSE` *synchronously* while the closing buffer is still in its data structures so a plugin's `beNotified` handler can call back into `NPPM_GETFULLPATHFROMBUFFERID(id)` and get the path. In Code++ the tab is removed from `Shell.tabs` before the queued notification fires, so that callback returns `-1`. Same applies to a future `NPPN_FILEBEFOREOPEN`. The fix is a synchronous-dispatch hook on `Shell` (a callback registered by the UI at startup that dispatches a single notification through `plugin-host::notify_all` mid-operation), used only for the BEFORE-* family. The deferred queue stays for the rest. `NPPM_RELOADBUFFERID`'s `with_alert == true` path needs the same mechanism — to synthesise a `PendingDialog::ConfirmReload` from inside `dispatch_plugin_message` so the user gets the same prompt the file-watcher path uses. Both gaps are documented in `docs/nppm-coverage.md` and tracked here so they land together with the rest of the plugin-host sync work in Phase 5.

- **`NPPM_SETBUFFERFORMAT` should issue `SCI_CONVERTEOLS` on the addressed buffer.** Today the dispatcher's `set_buffer_format` only flips `tab.eol` metadata — the Scintilla document's existing line-ending bytes are not rewritten. N++ additionally calls `SCI_CONVERTEOLS(SC_EOL_*)` on the buffer to normalise every line ending in place, so a plugin doing "set the EOL then save" produces a file with consistent line endings throughout. Code++'s metadata-only mutation is acceptable for empty buffers and for the immediate-after-load case (where there's nothing to convert yet) but not for general use. The fix needs UI-side cooperation: a `UiPlatform` method that takes a Scintilla doc pointer (from the addressed `Tab`) and the target EOL, swaps the editor's bound document to that pointer, sends `SCI_CONVERTEOLS`, and restores the original — the same doc-pointer-swap dance as Polish D's in-buffer FIF replace. Worth landing alongside the synchronous-notification work above since both require `Shell` to call back into the UI mid-dispatch.

- **Win32's dirty glyph can momentarily go blue on a restored buffer after edit-then-undo; GTK's does not.** Restored-but-unsaved buffers (untitled from backup, or a `DirtyFromBackup` saved file) are tracked in `Shell.unsaved_restore_ids` so they paint red and keep their recovery backup even though their Scintilla document sits at its save point. GTK's `refresh_active_dirty` ORs `Shell::is_unsaved_restore(id)` into every dirty poll, so its cached `Tab.dirty` stays red until a real save. Win32's `Tab.dirty` is driven solely by the `SCN_SAVEPOINTREACHED`/`SCN_SAVEPOINTLEFT` handler, which was **not** changed and does not consult the set — so on Win32, editing one character in a restored buffer and undoing it returns the doc to the seeded save point, `SCN_SAVEPOINTREACHED` fires, and the glyph flips to blue. **No data loss** — `Shell::tab_needs_backup` still ORs the id set, so the backup is retained regardless of the glyph — but the indicator is momentarily wrong. Backport the GTK fix to Win32's savepoint handler (consult `is_unsaved_restore` before clearing `Tab.dirty`) in the Phase 5 cross-platform pass; until then GTK is the more correct of the two here. (Could not be done in the same change that added the set because Win32 has no runner on the Linux dev host.)

- **Win32's close-confirm modal does not freeze `WM_APP_WAKE` dispatch; GTK's now freezes its wake — the two backends diverge on a tab-identity race.** When GTK's Save/Don't Save/Cancel prompt (the data-loss gate on closing a dirty tab) landed, a security audit found that a worker wake dispatched into the modal's nested main loop could `drain` the shell mid-prompt — `apply_load_result`'s failed-fresh-open branch and `apply_file_change` both move `active_tab` — sliding a different buffer under the user's decision. GTK closed it by prevention: a `DrainFreeze` RAII guard (a depth count, so a future Close All that loops the close path stays frozen until the outermost close finishes) makes `drain_shell` a no-op for the span of the close, then flushes once against the post-close state; the channels are unbounded so nothing is lost, only deferred. **Win32 has the same race still open** — `handle_close_active_tab_inner` documents it as accepted low-severity (its own comment: "the worst case is a confusing error message, not silent data loss"), on the reasoning that no current path clears an already-set `tab.path`. That reasoning is narrower than GTK's guard, which blocks the `active_tab`-shift vector outright. Backport the same freeze around Win32's modal pump in the Phase 5 plugin-host/sync sweep so the two backends protect the close prompt identically; until then, record that GTK is the stricter of the two here.

- **~~`EditorHandle` has no lifetime tie to the Scintilla widget it points at — decide the ownership model before tabs land on GTK.~~ Decided (Phase 5 m3): single view.** The question was real — `EditorHandle` is `Copy` with no `Drop` and holds raw pointers into a widget without expressing a lifetime, so nothing in the type system stops a copy outliving what it points at. `ui_gtk` resolves it the way `ui_win32` already did: one Scintilla widget is created at startup and never destroyed, removed or reassigned, and tabs get their own buffers through `SCI_SETDOCPOINTER` rather than their own views. The dangling-`direct_ptr` case therefore cannot arise, because there is no path that finalises a view.

  Recorded in three places rather than one, because a decision that lives only in a design document is not enforced: `EditorHandle::from_gtk_widget`'s safety section now states the *continuing* obligation (the original wording covered only the call, not the handle's later use), `GtkUiState.sci_widget`'s doc states how this backend discharges it, and `ui_gtk` carries a source-level guard asserting exactly one `scintilla_new()` with no destroy or reassignment. The guard is source-level on purpose: destroying the view would fault inside vendored C++ on the next direct call rather than fail an assertion, so a runtime test cannot observe the failure this exists to prevent. Mutation-verified against a second view, a destroy, and a reassignment.

  **This constrains any future backend.** A `ui_cocoa` that gives each tab its own `NSView` inherits the original problem and would have to tie the handle's lifetime to the widget instead.

- **~~Find-in-Files symlink hardening is Unix-only; Windows needs `FILE_FLAG_OPEN_REPARSE_POINT`.~~ Landed (Phase 5).** `read_capped` (`crates/shell/src/fif.rs`) grew a `#[cfg(windows)]` arm that passes `FILE_FLAG_OPEN_REPARSE_POINT` (`0x00200000`) through `OpenOptionsExt::custom_flags`. `CreateFileW` then returns a descriptor to the reparse point itself; `Metadata::file_type()` (via the handle-bound `GetFileInformationByHandleEx(FileAttributeTagInfo)` std makes for reparse-tag classification) surfaces `is_symlink() == true` and `is_file() == false`, and the existing `is_file()` gate refuses it as `NotARegularFile`. Bare-hex constant instead of pulling `windows::Win32::Storage::FileSystem` into `codepp-shell` — the value is ABI-frozen since Windows 2000.

  Windows adversarial coverage: two new tests, both `#[ignore]`d because their setup (`std::os::windows::fs::symlink_file`) needs `SeCreateSymbolicLinkPrivilege` (developer mode). `#[ignore]` was chosen deliberately over a runtime skip after the security audit demonstrated that a runtime skip is invisible in `cargo test`'s default output — a runner without developer mode would silently drop coverage while reporting fully green. The two ignored tests are `read_capped_refuses_a_symlink` (pins the fix — the audit mutation-tested that neutralising `FILE_FLAG_OPEN_REPARSE_POINT` surfaces here as an `Ok(_)` where a reject was required) and `atomic_write_replaces_a_symlink_at_the_destination` (closes the sub-item this section previously flagged as untested — `NamedTempFile::persist` via `MoveFileExW` replaces the destination reparse point rather than following it). A non-ignored `read_capped_refuses_a_junction` runs on every runner (junctions need no privilege via `mklink /J`) as belt-and-suspenders coverage — it does not itself regression-cover `FILE_FLAG_OPEN_REPARSE_POINT` (its reject fires via `ERROR_ACCESS_DENIED` on the directory open, independent of the flag), documented plainly in the test's own comment.

  CI runner requirement recorded in `docs/DEVELOPMENT.md` §2.6: the `windows` runner needs developer mode enabled and runs the workspace tests with `cargo test -- --include-ignored`, otherwise the fix has no live regression coverage.

- **Decide, explicitly, whether the 43% memory rise from m1 is accepted.** §8 now carries the per-mapping attribution rather than a guess: PSS went 8.17 MB (m1) to 11.81 MB (m3), and the growth is **+2.60 MB of `.text`, +0.85 MB of `.rodata`, and exactly zero heap**. So it is static footprint — code and tables that are resident because startup executes them — not a leak, and it does not scale with the number or size of open files. That is the strongest case for accepting it, and 11.8 MB is 47% of the 25 MB budget. It is still past §8's own ">20%" bar, and §8 says non-negotiable with no headroom clause, so the rule wants an explicit answer rather than a silent pass. If the answer is "reduce it instead", the three untried levers are named in §8 — compile `lang_theme`'s 85-branch chain to a table lookup, `opt-level = "s"`, or `lto = "fat"` — and each is a measurable experiment, not a guess. Whoever decides should also fix the baseline: §8's m1 row is the *only* figure the doc ever recorded before m3, which is how a two-milestone drift went unnoticed; recording PSS at every phase boundary would have caught it at m2.

- **Find what stalls ~1% of keystrokes above roughly 15 characters per second.** §8 now characterises the tail properly — 5 016 samples at a fast-human rate put p99 at 4.62 ms, inside the 5 ms budget — but at 20 char/s p99 jumps to 65 ms while p50 and p90 barely move. That shape is a cliff, not a backlog: something occasional blocks for tens of milliseconds rather than everything getting slower. Two candidates were tested and refuted, so do not start there: the 7-second session auto-save (interval raised to 100 000 s, p99 unchanged at 65.4 ms) and Lexilla restyling (same-size plain-text file with no lexer, p99 unchanged at 60.5 ms). It is content-independent and rate-dependent, and the worst sample at human rates was 17.8 ms, so it never reaches the budget in normal use.

  Next step is a profiler, not another black-box run — the remaining suspects (GTK frame-clock scheduling, compositor frame misses, a status-bar label width change forcing a relayout, GDK event coalescing) are indistinguishable from the outside. `--perf` now reports the arrival distribution alongside latency, which is what any repeat of this needs: the input rate has to be measured rather than assumed, and it must be checked against the numbers in §8 rather than against a tool's `--delay` flag.

- **A failed load leaks its Scintilla document when the tab was bound before the load resolved, on every backend.** `Shell::bind_active_view` materialises a document for any active tab that lacks one, with no `pending_load` gate — so a tab whose load is still in flight acquires one as soon as the user clicks back onto it, and `Shell::load_npp_session` reaches the same state deterministically by restoring the recorded-active tab mid-flight. If that load then fails, `apply_failed_load` removes the tab, and `self.tabs.remove` drops its `scintilla_doc` with it. `close_active_tab`'s `ClosedTab` is the only channel by which a document pointer ever reaches a backend's `SCI_RELEASEDOCUMENT`, so nothing frees it.

  Long-standing rather than new — the pre-`open_file_replacing_scratch` code did exactly this — and surfaced by the audit of that change, which established the two reachable triggers above. Not a data-loss bug (the leaked document is empty) and not unbounded (one per failed open of a tab the user happened to visit while it loaded), but it is a native-resource leak reachable from ordinary use.

  **Closing it needs a `UiPlatform` method the trait does not have**: something like `release_doc(&mut self, doc: isize)`, implemented as `SCI_RELEASEDOCUMENT` on all three backends, called from `apply_failed_load` before the `remove`. That is a trait addition touching all three, so it belongs with the Phase 5 cross-platform sweep rather than being bolted on from a macOS-only host. A default no-op implementation would be the wrong shape here — it would leave two backends silently leaking while looking implemented.

- **A background load left its tab's Scintilla document stale, and `Save All` then wrote that document over the real file.** Reported by a user on macOS: File → Open All Recent Files opened every file, and the first showed its filename over an empty buffer; reopening the same file through File → Open worked, which made it look like a loader bug rather than a binding one.

  `bind_active_view` filled a tab's document only when `scintilla_doc == 0`. That is a correct proxy for "never populated" exactly while every background load targets a *fresh* tab — the assumption `apply_load_result`'s own comment states. `open_file_replacing_scratch` breaks it by re-targeting a load onto the startup `new 1`, whose document already exists: the first file in a multi-open is the only one that reuses the scratch, and the opens that follow move `active_tab` off it before its load lands. New `Tab::doc_needs_text` records the case and a new `Shell::bind_and_fill` — the single place that knows how to make a document match its tab — consumes it.

  **The pre-commit gate found the reported symptom was the mild half of the problem.** `Shell::save_all` bound each tab's document with a bare `activate_tab` and read it straight back with `get_buffer_text` to write to disk, so a stale binding there *overwrote the file with the wrong bytes* rather than merely displaying them — reachable as Open All Recent Files followed by Save All without ever clicking the first tab. That predates the flag; it is what made the flag worth having rather than what the flag caused. Worse, the same path applied to a tab whose document was never created at all: `activate_tab(idx, 0)` hands back an *empty* document, so an unvisited background tab's file was rewritten empty. `save_all` now routes through `bind_and_fill` like every other binder, and `Tab::doc_needs_text`'s doc states the obligation for the next one.

  **Filling must never happen over unsaved edits**, and that hazard is created by the fix rather than pre-existing. `confirm_reload` re-targets a load onto whichever tab holds the path, active or not, and is reached from the file-watcher prompt, File → Reload and — with no prompt at all — a plugin's `NPPM_RELOADBUFFERID`. Before the flag, a background reload was inert: it updated `Tab.text` and left the document alone. With it, the next activation would have filled through `set_buffer_text`, which empties the undo buffer and sets the save point — silent, unrecoverable loss of the user's work, on every backend and with no user action beyond clicking a tab. The flag is therefore gated on `is_doc_dirty` where it is *set*, and again where it is *consumed*, because Replace-in-Files can dirty a background document in between; `apply_open_buffer_replacement` also clears it, for the reverse ordering its own `is_doc_dirty` check cannot see.

  **The first version of that guard asked the wrong question, and the audit reproduced the consequence against a real `Shell` before it shipped.** It checked `is_doc_dirty` alone — but a buffer restored from a crash-recovery backup is seeded through `set_buffer_text`, which *sets the save point*, so Scintilla reports it clean while its contents exist nowhere but memory. `Shell::unsaved_restore_ids` is the durable record, and `tab_needs_backup` had always ORed the two; the new guards did not. A plugin's `NPPM_RELOADBUFFERID` on a background restored buffer therefore flagged it, and the next click replaced the recovered work with the on-disk text — then `save_all` persisted that and cleared the recovery marker, so nothing recorded the work had ever existed. All three guards now go through one `has_unsaved_work` helper, `apply_open_buffer_replacement`'s pre-existing `is_doc_dirty` gate included, since Replace-in-Files had the same blind spot. `FakeUi`'s dirty flag was per-*fixture* rather than per-document, which is the second reason an ordinary test could not have caught this; it now takes per-document overrides.

  Reproduced end to end against the real app, both directions: without the fix the first tab reports `("file1.txt", 0, "")` while the other two are correct; with it, all three carry their content. Four shell-level regression tests, all mutation-verified, and each asserts its own precondition so none can pass vacuously.

  **`FakeUi` was upgraded to model one text per document**, which is the reason this class of bug could ship: its single shared text slot meant `save_all_writes_every_titled_tab` passed while `save_all` was binding an unpopulated document, because the previous tab's text was still sitting in the slot. Two existing tests' expectations encoded that leak and were corrected — they now assert each file gets *its own* buffer's content.

  **Win32 is not covered by the `bind_and_fill` half and keeps a pre-existing gap.** `ui_win32` has no `bind_active_view` call site at all: `handle_tab_selchange` carries its own materialise-on-first-activation logic, gated on `scintilla_doc == 0`, so it ignores `doc_needs_text`. The reused-scratch case cannot reach it (Win32 does not call `open_file_replacing_scratch` — see the entry below), but a background *reload* can, and leaves a stale document exactly as it did before. No regression, since that path was equally stale before the flag existed; the `save_all` fix, being shell-level, does reach Win32. Closing it means routing Win32's tab activation through `Shell::bind_active_view` as `ui_gtk` and `ui_cocoa` do, which is a change to the largest crate in the workspace with no runner on the macOS development host.

- **`ui_gtk` and `ui_win32` do not yet replace the untouched `new 1` on open; the shell API for it landed with the macOS fix.** `Shell::open_file_replacing_scratch` is cross-platform and needs only a call-site swap plus a three-send helper (`SCI_GETLENGTH == 0 && !SCI_CANUNDO && !SCI_CANREDO`) on each backend — see `ui_cocoa::editor_is_pristine`, and note the redo half is load-bearing rather than defensive (typing one character and undoing it leaves `SCI_CANUNDO == 0` but `SCI_CANREDO == 1`, measured).

  The call sites are named here so the follow-up is unambiguous, because picking the wrong one is the way to get this subtly wrong: only *user-initiated* opens should opt in. On GTK that is `menu::open_paths` (`crates/ui_gtk/src/menu.rs`), which serves File→Open and drag-and-drop — and only its first iteration can match, since after one open the workspace is no longer a lone tab. Session restore (`lib.rs`, two sites) and the Find-in-Files jump (`fif.rs`) must keep the plain `open_file`: a restore is replaying a saved workspace, and a FIF jump is navigation, neither of which should consume a buffer. Win32 has around eight call sites and needs the same triage.

  Not done in the same change because there is no Linux or Windows runner on the macOS development host, and this is a data-loss-adjacent gate — it decides whether a buffer is discarded — so landing it unexercised on two backends is exactly the trade this project declines. The `Shell`-level gate and its tests do run on every runner, so the risky half is already covered; what is untested per backend is only the `editor_is_pristine` measurement and which call sites opt in.

- **`ui_gtk`'s Unfold All ceilings do not bound anything, because the final reveal re-enters the lazy loader.** Found by the macOS m4d gate while porting the same walk. `tick_unfold`'s completion arm calls `expand_all()` unconditionally, under a comment asserting every row is already populated — which holds when the queue *drained* and not when `UNFOLD_MAX_FOLDERS` or `UNFOLD_MAX_ROWS` stopped it. `GtkTreeView::expand_all` walks every row and fires `row-expanded`, which is where `populate_children` hangs, so every folder the ceiling declined gets read anyway: recursively, synchronously, in one unbatched call. That is strictly worse than no ceiling, since the batching is what kept the UI responsive.

  Measured on the Cocoa side, which has the identical shape: on a 340-directory tree with the folder ceiling lowered to 5, the recursive reveal populated all 341 directories against the correct 20. The fix is `ui_cocoa::workspace::expand_populated` — expand only folders already read, leaving the rest collapsed and still lazily expandable, which is what the ceilings' own documentation always claimed happened. Not fixed on GTK here because there is no Linux runner on the macOS development host, and the failure mode is a UI hang on a pathological tree, which is exactly the thing not to land unexercised.

- **`ui_gtk::style_config` puts an unsanitized font name into its font combo, and `apply_default_style` ignores its own documented transparency floor on all three backends.** Both found by the macOS m4g audit.

  (1) `combo.append_text(current)` inserts a face read from `styles.xml` verbatim, so a name carrying bidi controls renders reordered — the same class as the three incidents §7.4 already records. The fix is not a plain sanitize: the combo's text is *also* the value read back by `read_styles`, so substituting would rewrite the user's stored font. `ui_cocoa::style_config` shows the shape — sanitized titles plus a side table of real faces read back by index.

  (2) `apply_default_style` clamps `Transparency::percent` to `0..=100` in all three backends, while the field's own doc states a 20% floor that "the dialog's slider enforces". A hand-edited `styles.xml` with `percent="0"` therefore yields a fully transparent — still focusable, still clickable — main window, with no in-app way to see what to click. `Styles::clamp` bounds the font name's length and nothing else. The floor belongs in `clamp`, so every consumer inherits it rather than three backends each remembering; doing it there is a `core` change that wants all three exercised.

  Neither is fixed here because there is no Linux or Windows runner on the macOS development host, and (2) is a one-line change in three places that is worth landing together rather than leaving the backends disagreeing about their own floor.

- **A plugin that sends `SCI_*` from its own thread reaches Scintilla off the main thread on both non-Windows backends.** Found by the macOS m5 audit, and it is a characteristic of the SDK's non-Windows transport rather than of either backend. On Windows, `SendMessage` from a plugin's worker thread is marshaled by the OS onto the thread that owns the window, so a plugin written against that semantics is safe by construction. Off Windows the SDK forwards straight to the host callback on whatever thread called it: `NPPM_*` degrades safely (the state is a `thread_local`, so the dispatcher finds nothing and returns "declined") but `SCI_*` reaches `objc_msgSend` on a `ScintillaView` — or `scintilla_send_message` on a `GtkWidget` — from the wrong thread, which both toolkits document as undefined. That branch deliberately bypasses `with_state`, and must, so it has no backstop.

  No in-tree plugin does this and DESIGN.md §6.5 already accepts that an in-process plugin can crash the app, so it is recorded rather than guarded. The two obvious fixes both need a decision: **refusing** a cross-thread `SCI_*` is safe but diverges from the Win32 semantics a ported plugin was written against, and **marshaling** it properly means a synchronous round trip onto the UI thread (`DispatchQueue::main().exec_sync` / `g_main_context_invoke_full` plus a completion), which reintroduces a deadlock risk if the UI thread is itself waiting inside a plugin call. Whichever is chosen, both non-Windows backends have to choose the same one — this is exactly the sort of per-backend answer that produces drift.

- **`ui_gtk`'s Plugin Manager does not freeze the drain while its modal is up.** Found by the macOS m5 review while comparing the two. `ui_gtk::plugin::show_plugin_manager` calls `dialog.run()`, which spins a nested GTK main loop, with no equivalent of the `DrainFreeze` guard `ui_cocoa` holds around its own `runModal` — so a worker wake dispatched into that loop can `drain` the shell mid-dialog. Same class as the close-prompt race §7.4 already records in the other direction (there GTK is the stricter of the two and Win32 the laxer). Lower severity than that one, because the manager's snapshot is index-keyed against a registry that nothing worker-driven mutates — the realistic worst case is a stale row rather than a wrong plugin being disabled — but the argument for it being unreachable is again about what a *user* can do, which is the premise that stops holding the moment a plugin or a timer can touch the shell. Not fixed here because there is no Linux runner on the macOS development host; the fix is one RAII guard, mirroring `ui_cocoa::plugin::show_plugin_manager`.

- **Plugin menu-item shortcuts are not implemented on any non-Windows backend, and on macOS they need more than wiring.** A `FuncItem` carries a `ShortcutKey`, and neither `ui_gtk::plugin` nor `ui_cocoa::plugin` reads it — so DESIGN.md §6.4's third lazy-load trigger ("fires a hotkey owned by the plugin") does not exist off Windows, and a plugin that documents a keyboard shortcut simply has none. On GTK the fix is mechanical (`gtk_widget_add_accelerator` on each item as it is built). On macOS it is not: the Plugins menu's items are built from `menuNeedsUpdate:`, and m4f established by measurement that **AppKit does not call `menuNeedsUpdate:` when it searches for a key equivalent** — so a shortcut on a lazily-built item is dead until the user happens to open the menu once, which is the exact shape of silently-half-working this backend keeps having to fix. Closing it means either a static tail carrying the shortcuts (as the Recent Files region does, which is why that region's three commands are static) or accepting that plugin shortcuts arm on first menu open. Worth deciding rather than drifting into, since the second option is defensible — nothing is loaded before that open either.

- **The `HWND`-shaped `UiPlatform` methods keep their trait defaults on both non-Windows backends, so a plugin cannot dock a panel or add a toolbar icon there.** `create_plugin_scintilla`, `register_dock_dialog` (which does a literal `SetParent` on Win32), `show_dock_dialog`, `hide_dock_dialog`, `dock_hwnd_by_name`, `register_modeless_dialog` and `add_toolbar_icon` are all defaulted on GTK and, since macOS m5, on Cocoa too. A plugin that only transforms buffer text — which is all four in-tree ones, and most of the useful third-party ones — is unaffected; a plugin with its own docked panel degrades to "the menu item does nothing visible". This is a design question rather than an implementation gap: the two backends need a shared answer to what a plugin-owned panel *is* when the handle it is given is not message-addressable, and inventing one per backend is how the two drift. Recorded here so the m5 completion is not read as full plugin parity.

- **`ui_gtk` styles UDL buffers but offers no way to select one, and the comment explaining why is stale.** Found by the macOS m4e port. `ui_gtk::udl` is complete — `apply_lang` routes to the container lexer, `on_style_needed` answers `SCN_STYLENEEDED`, `resolve_lang_label` names the buffer — but `build_language_menu` appends only `build_udl_submenu` and never enumerates `registry.entries()`. UDL ids live in a dynamic space above the built-in constants and are absent from `LANG_TABLE`, so nothing detects them by extension either; the only route into GTK's UDL styling is a `tab.lang` restored from a `session.xml` written on another platform, or hand-edited.

  `build_udl_submenu`'s own doc comment states the reason as *"GTK's `apply_lang` does not style UDL buffers (it logs and falls through — see `platform.rs`) … They land when UDL styling does"*. That stopped being true when `ui_gtk/src/udl.rs` landed; `platform.rs` now calls it and returns early on a UDL id. So the condition the comment sets has been met and the rows were never added.

  The fix is `ui_cocoa::menu::rebuild_udl_rows` ported to GTK's `connect_show` handler, which already exists for the language marks — plus deleting the stale rationale. Not done here because there is no Linux runner on the macOS development host, and the milestone's own bug (a tagless submenu child colliding with `L_TEXT`'s id 0 and ticking the wrong row) is exactly the kind that wants a hands-on look at the menu it changes. Note GTK's mark path is `CheckMenuItem`-based rather than tag-based, so it does not inherit that specific hazard.

- **`ui_gtk`'s Find/Replace has two gaps the Cocoa port fixed: stale chrome after a replace, and an unsanitized query seed.** Both were found by the macOS m4a gate while comparing against `ui_gtk::search` as the reference, and both are in that reference rather than in the port. (1) `do_replace_one` / `do_replace_all` mutate the buffer inside a `with_state` closure, and GTK's `sci-notify` is emitted synchronously from inside the edit — so the notification re-enters while the borrow is held, `with_state` declines, and the tab's dirty marker and the status bar stay stale until an unrelated event repaints them. `ui_gtk/src/lib.rs` documents this exact contract; these two call sites do not honour it. The Cocoa fix is one `refresh_chrome()` after each borrow returns. (2) `open_dialog` seeds the query field from the selection with no display-sanitization check, while the Find-in-Files *directory* field in the same function is explicitly guarded with a written rationale — so the omission on the query field reads as an oversight rather than a considered exception. The Cocoa fix refuses to seed a display-hostile selection rather than substituting into it, because the field's contents are a search parameter and a substitution would search for the wrong thing. Neither is fixed on GTK here because there is no Linux runner on the macOS development host; both are one-line changes mirroring `ui_cocoa::search`.

- **~~macOS scrollbars.~~ Fixed on the third attempt (Phase 5), and the two failed ones are recorded because each looked correct.** The cause is in vendored code: `SCIScrollView::tile` calls `[super tile]` and then shifts the content view right by the line-number margin's width and shrinks it by the same, with no allowance for scrollers that *take space* rather than float over the content. `ScintillaCocoa::SetScrollingSize` re-assigns `hasVerticalScroller`/`hasHorizontalScroller` on every call, so any document resize re-tiles.

  Attempt one forced `NSScrollerStyle::Legacy` for a permanently visible bar, which is what the other two backends have. It worked until the first line longer than the viewport: the re-tile then left the clip view covering the scrollers and **both** disappeared. Measured — the clip went from 1019×531 to 1036×548 inside a 1080×548 scroll view while the scroller frames stayed put. `ScintillaView.mm:1474` carries `//[scrollView setScrollerStyle:NSScrollerStyleLegacy];`, commented out, so upstream met this too.

  Attempt two reverted to AppKit's overlay default and called `flashScrollers()` whenever the scroll position changed. That is the documented way to show overlay scrollers for programmatically scrolled content, and it is *not enough here*: Scintilla scrolls its own content, and the flash is a brief fade the user reported never seeing at all. Instrumenting showed the flash firing exactly once, at startup.

  What works is to force Legacy **and repair the geometry `tile` should have produced** — clip width = view width − gutter − vertical bar, height = view height − horizontal bar — re-asserted after every `SCN_PAINTED`, since that is what follows a re-tile. Host-side rather than a patch to the vendored tree, the same shape as `clamp_scroll_width_to_viewport` and for the same reason (§4.1). It is idempotent, so a paint where nothing moved costs one rect comparison. Verified by driving the app: the bug reproduces on the long line, the repair restores 1019×531, and a second repair changes nothing. The arithmetic is a pure function with unit tests including a transposed-axis case, on this project's usual reasoning that off-by-one rect maths is what a hands-on demo is worst at catching.

  A fourth report followed, and it was the *other* half of the same floor. `clamp_scroll_width_to_viewport` only ever raises `scrollWidth`, which is right while the window keeps its size — the floor is what stops the blank area right of short lines being unclickable — but the raised value outlives the viewport that justified it. Maximising and un-maximising a three-line file therefore left the document as wide as the old clip and a horizontal scrollbar appeared for content that was not there; it cleared on the next maximise or tab switch, both of which re-seed.

  **The obvious fix is wrong, and the pre-commit gate caught it before it shipped.** Re-seeding on a viewport change — resetting the width to 1 so Scintilla's tracking recomputes it from actual content — reads correctly and passed the test written for it. But `SCI_SETSCROLLWIDTH` also zeroes `lineWidthMaxSeen`, and tracking only re-raises during a subsequent `Paint`, so reading the width back in the *same* pass and flooring it at the viewport pinned it there. Measured after the reviewer raised it: with a 4 000-character line on screen, resizing 1500 → 900 collapsed the document from 26 525 pt to 839 pt and it did not recover, putting the rest of that line out of reach. Worth recording that the first attempt to reproduce it *failed* — the probe resized the window to the size it already had, so the gate never fired and it proved nothing. The finding was real; the test was not.

  What ships instead lowers the floor only when the width is *exactly the value this function last installed*, which is the precise statement of "nothing but the floor is holding it up". A content-derived width never matches that except by coincidence, and a coincidence is harmless because tracking re-raises it on the next paint while the line is still on screen. No window exists in which the width is 1, so the document view cannot collapse. Verified in both directions: a short-line file's document follows the clip through grow and shrink with nothing scrollable, and a long line on screen keeps its 26 525 pt range across the same resize.

  Two ordering details are load-bearing and easy to get wrong. The repair must run *before* `clamp_scroll_width_to_viewport` in the same notification arm, because that reads the clip's width and would otherwise measure the wrong, scroller-covering one and raise a floor that only ever rises. And the style must be set before the first repair, which is a no-op while the scrollers are still overlay.

- **macOS misses two of the three §8 budgets — cold start and keystroke latency. Memory passes, and the reported miss was a measurement error.** *(Same weight caveat as the Win32 entry below: §8 calls these budgets non-negotiable, so this deserves separate triage rather than sitting in a polish list.)* Measured at Phase 5 m1, release build, one empty buffer: `phys_footprint` **73.0 MB against 25 MB**, and cold start **~111 ms against 80 ms**. The full numbers and the partial attribution are in §8. The memory miss is the larger and the less understood of the two: `vmmap` shows the process mapping WebCore, JavaScriptCore, SwiftUI, GeoServices and ANECompiler — none of which Code++ links — but those are clean COW text pages that `phys_footprint` should not be counting, so they are a lead rather than the answer. What needs explaining is 68.5 MB of *resident writable* memory of which only 16.9 MB was ever written. Next step is `malloc_history` / `heap` against a live process; a second `vmmap --summary` will not add anything.

  **Both figures moved by m4b's re-measurement, and the cold-start one is now a different — worse, and better-understood — problem.** `phys_footprint` is ~77 MB, roughly unchanged. Cold start is **~235 ms against 80 ms, about 3×**, and the earlier ~108–122 ms figures are retracted: they closed the interval before `-[NSApplication run]`, so they measured neither a first draw nor the same span the other two backends measure. §8 carries the per-phase attribution; the two suspects this entry previously named — the toolbar's PNG decoding and the menu tree — were measured and are **both refuted**, at 6.9 ms and 6.7 ms.

  What the attribution leaves is one dominant item and two ordinary ones. **`NSApplication::sharedApplication` costs 55–61 ms on its own**, i.e. 70–76% of the whole budget is gone before Code++ constructs anything, and putting the binary in an `.app` bundle does not change it (61–69 ms bundled — tested, because it was the obvious hypothesis). Code++'s own share is window plus chrome construction (~37 ms) and the post-build startup work of styles, session restore and view settings (~35 ms).

  **That AppKit cost is a platform floor, not something Code++ provokes**, and a minimal-app reference now bounds the whole thing rather than just that one call. A twelve-line Objective-C program — `NSApplication`, one 1024×768 `NSWindow`, one `NSView` filling white — measures **149.7 / 182.9 / 195.0 ms from `main()` to first paint** and settles at **13.6 MB**. Win32's *entire* cold start is 94 ms, i.e. below the macOS floor for a blank window. §8 carries the full breakdown, including the 1 036 dylibs (WebKit, JavaScriptCore, WritingToolsUI among them) an empty Cocoa window ends up holding.

  **So the two budget misses are different problems, and only one of them is ours.**

  *Keystroke latency is the third miss, and unlike the other two it is now diagnosed.* p99 ≈ 20 ms against 5 ms, worse than either other backend. **Every keystroke repaints every visible line, and each line costs a fresh `CTLineCreateWithAttributedString`** — CoreText typesetting and glyph encoding, per line, per keystroke. The thread is busy for the whole interval rather than waiting for a frame (main-thread CPU equals wall time to within 0.04 ms), and latency scales with window height: p99 6.4 ms at 14 visible lines, 21.1 ms at 64. §8 has the profile, the per-phase split, and **five refuted hypotheses** — frame scheduling, the status-bar refresh, `SC_CACHE_PAGE`, `SC_PHASES_ONE`, and this backend's own `SCN_PAINTED` hooks — none of which should be re-tried.

  The full-bounds repaint is not something this backend chooses: `NSWindow`'s content view is unconditionally layer-backed on modern macOS (169 of 169 views measured), and the layer redraw hands Scintilla the whole rect. **So the one real fix is to cache `CTLine` objects per (text, style) run inside Scintilla's Cocoa `SurfaceImpl`** — turning a repaint of an unchanged line from a typeset into a draw. That is a patch to the vendored tree, which §4.1 deliberately keeps unforked, so it needs a decision rather than a commit: either carry the patch (and own it across Scintilla bumps, alongside the two host-side workarounds §7.4 already records for the same backend), or accept that macOS types at ~20 ms p99 on a full-height window. Neither other backend has the problem, because neither re-typesets per paint — Win32 goes through GDI/DirectWrite and GTK through Pango, both of which cache.

  *Cold start is the platform's.* Code++'s own share is the ~40–85 ms above the floor; driving it to zero still lands at ~160 ms against an 80 ms budget. The open question is no longer "what is slow" but "what should the target be" — whether §8 should give macOS its own documented cold-start figure the way it already gives each platform its own *memory* metric, with the honest justification that a 150 ms platform tax is not something an application can architect away. Worth one run each on Intel and on an older OS version first (the harness is a dozen lines, and the WebKit/WritingTools names suggest this is recent).

  **Memory is no longer a miss at all — 18.5 MB against 25 MB — and the reported miss was a measurement error.** §8 has the full correction: every earlier figure was taken by launching the binary and sampling it, which restores the previous session, so what was measured was whatever files the developer last had open rather than §8's stated "one empty buffer". Clearing `session.xml` first gives 18.5 MB; the accumulated session that produced the 76 MB reading held five files and a crash backup. Keep the sRGB pin — the per-surface halving was observed directly — but its headline "35% saving" is retracted along with the rest, since re-measured clean it is 18.9 → 18.5 MB. The paragraph below is the superseded reasoning, kept because the mechanism it describes is still right and only the magnitudes were wrong.

  **That 18.5 MB did not reproduce at m4c; the discrepancy is now closed, in favour of the smaller figure.** *(Superseded — see the m5 block in §8: 19.4 MB, confirmed by two independent instruments. The paragraph below is the m4c-era reasoning, kept because the question it raised was the right one.)* Same machine, same release profile, same "delete `session.xml` first" protocol: **47.1–47.4 MB**, settling there from 57 MB over the first eight seconds. Measured against the milestone's own stashed baseline it is flat, so it is not m4c's — it is either a pre-existing drift across m4b→m4c or a difference in how the two measurements were taken that has not been identified. Attribution at rest: IOSurface 20.5 MB, `MALLOC_SMALL` 14.4 MB dirty. Two candidates were ruled out cheaply — a stale crash-recovery backup (the directory held one empty file) and the sampling instant (the figure is stable from ~8 s). Whoever picks this up should establish which of the two numbers is the honest one *before* treating either as a budget verdict, because 18.5 MB passes §8 and 47 MB does not.

  *Memory was misattributed twice before that, and the second attribution stands as a mechanism.* This entry first said the ~73 MB looked like an AppKit-established floor because it did not move across milestones; it does not move because its dominant term is the window's compositing surfaces, which depend on window size. The follow-up lead — the scroll-edge-effect `NSVisualEffectView` — was then **tested and refuted**, saving nothing. The actual cause was the surfaces' *pixel format*: CoreAnimation gives a window on a wide-gamut display half-float RGBA (`RGhA`, 8 bytes per pixel). **Pinning the window to sRGB drops that to `BGRA` and the footprint from ~77 MB to ~50 MB — a 35% saving, landed.** §8 has the measurement and the pixel-level check that it changes nothing on screen.

  What remains is ~50 MB against a 25 MB budget, and it is compositing buffers sized by the window the user opened, not heap — a 400×300 window is already 27.6 MB. So the memory question is now the same shape as the cold-start one: not "what is leaking" but "is a budget written against Win32's private working set meaningful for a metric that counts GPU-shared window buffers". Three further levers exist and are untried: whether the three buffers can be reduced to two, whether the surfaces have to cover the whole window, and — the cheapest — **pinning the secondary windows too**. Only the main window is pinned today; the Find/Replace `NSPanel`, the alerts and the open/save panels still get wide-gamut backing while they are on screen. They are small and transient so no saving is claimed, but the split means two windows in the same app behave differently, which is the kind of asymmetry this document has been bitten by before. One shared helper at each construction site, and a measurement to say whether it is worth anything.

  It also means the cross-platform comparison was never like-for-like: on Linux those compositing buffers live in the X server, not in the editor's PSS. Whatever is decided about the target, `phys_footprint` and PSS counting different things needs to be stated in §8 rather than left implicit.

  Two things worth deciding alongside it rather than after: whether any of those frameworks can be kept unmapped at all (an `.app` bundle with a restrictive `Info.plist`, or avoiding whichever AppKit call pulls SwiftUI in, are the obvious things to test), and whether m1's numbers should gate m2 or simply be tracked. Recording them now is deliberate — §7.4's own post-mortem on the Linux memory drift concluded that measuring once at the end is exactly how a regression goes unnoticed, so every macOS milestone from here should re-record both figures.

- **~~macOS: only the text itself was clickable — the empty space to the right of a line was not.~~ Fixed (Phase 5, post-m3b).** The residual of the fix below, and reported straight after it: double-clicking in the blank area right of a line's content to select the line — an ordinary gesture that works on Win32 and GTK — did nothing.

  Same root as its predecessor, one level subtler. Scintilla's Cocoa backend sizes the `NSScrollView` document view from `scrollWidth` and clamps only the *height* to the clip rect (`cocoa/ScintillaCocoa.mm::SetScrollingSize`: *"Ensure all of clipRect covered by Scintilla drawing"*), never the width — `docWidth = Wrapping() ? clipRect.width : scrollWidth`. Neither other backend shows this, because neither sizes a view from `scrollWidth`; there the whole editor widget is the click target.

  Fixed host-side rather than by patching the vendored tree (DESIGN.md §4.1 keeps it unforked): `clamp_scroll_width_to_viewport` raises `scrollWidth` to the clip width whenever tracking leaves it lower, re-asserted on `SCN_PAINTED` (tracking recomputes during layout, so a one-shot floor would not survive) and immediately after a rebind. Tracking stays on, so a genuinely long line still scrolls and the width still shrinks back when that line is deleted — this only raises the floor. The clip width is read from the live `NSClipView` rather than computed as "view width minus margins minus scroller", so it stays correct as those change.

  Measured both directions: a short-line file gives `scrollWidth == visible == 956` with a click 800 px right of the text landing on `SCIContentView` and moving the caret; a 600-character line gives `scrollWidth 3973 > visible 956`, stable across samples, so horizontal scrolling is intact and the floor does not oscillate against tracking.

- **~~macOS: `SCI_SETSCROLLWIDTH(1)` without tracking collapsed the document view to one point wide, killing mouse input.~~ Fixed (Phase 5, post-m3b).** The third and actual cause of "the mouse stops working", after two earlier fixes that were each real but not this. - **~~macOS: the window was never key and the app never active, so mouse input did not work.~~ Fixed (Phase 5, post-m3b).** Reported by a user testing the m3b build: typing and deleting worked, but clicking in the editor did nothing — no caret placement, no selection.   Diagnosed by measurement rather than inspection, because every layer looked correct: the view hierarchy, frames and first responder were all right (`SCIContentView` at the expected size, first responder as expected), and a synthesized `NSEvent` pushed through `NSApp.sendEvent` moved the caret from 0 to 20 — proving the whole in-process path worked. The discriminator was activation state: a bare `./codepp` reported `app_active=false has_key_window=false` from inside the run loop, while the *same binary* copied into a minimal `.app` and launched with `open` reported all true.   **Why no test caught it, and what now does.** The failure needs a real run loop and a real window server and manifests as *absence* — no event arrives. The display-gated `cocoa_smoke` test has no run loop (it is `harness = false` so it owns the main thread, not so it pumps events), and every milestone demo to that point verified logic through `session.xml` round-trips, which never required the app to be interactive. A source-scanning guard in `ui_cocoa` now asserts that activation appears in `activate_main_window` and *not* in `run()` — the same tool `ui_gtk` uses for its single-view invariant, and chosen for the same reason: the property is unobservable at runtime in CI but trivially checkable in the source. Mutation-verified (putting `makeKeyAndOrderFront` back into `run()` fails it).

  Worth carrying forward: an `.app` bundle also fixes it, and §9.2 already schedules one for macOS distribution — but the bundle should not be the reason input works, since development happens through `cargo run`.

Win32 does *not*: verified against a real Notepad++ install on Windows 11, its horizontal scrollbar is hidden until a line overflows. The cause is a Scintilla platform-backend difference, not a Code++ bug. Win32 Scintilla drives the *native* OS scrollbar via `SetScrollInfo`, and Windows auto-hides a native scrollbar whose whole range is visible — free, no Scintilla logic. GTK Scintilla packs its own `GtkScrollbar` and shows it unconditionally (`ScintillaGTK.cxx` `showSBHorizontal = horizontalScrollBarVisible && !Wrapping()` — no content-width check). The one lever to hide it host-side, `SCI_SETHSCROLLBAR`, sets the *same* `horizontalScrollBarVisible` flag that gates Scintilla's width-tracking (`Editor.cxx:1895`), which the `clamp_horizontal_overscroll` fix (`06c5acf`) depends on to keep `scrollWidth` equal to real content width — so toggling it to auto-hide would either freeze that tracking or flicker the bar on/off around edits near the viewport edge. Not worth that risk for a cosmetic, already-non-draggable bar; recorded here rather than fixed. If pursued later, the clean approach is probably a small patch to the vendored GTK backend's `SetScrollBars` to gate `showSBHorizontal` on `scrollWidth > pageWidth` (keeping `horizontalScrollBarVisible` — and thus tracking — untouched), landing alongside any other vendored-Scintilla carries.

### 7.5 Phase 5 cross-platform parity checklist

A user opening Code++ on Linux or macOS in Phase 5 should see *every* user-visible feature that's already in Win32, behaving the same way. The Phase 5 demo (DESIGN.md §7.2) is the functional gate; this checklist is the explicit work list so nothing slips. It splits cleanly into "already cross-platform — just plug in `UiPlatform`" and "needs new per-platform plumbing."

**Already cross-platform (no Phase 5 design work; the GTK/Cocoa backends inherit it for free by implementing the existing `UiPlatform` trait + `Shell` API):**

- **Session persistence.** `core::session::{Session, Tab, WindowGeometry}` round-trip via `quick-xml`; `Shell::save_session` / `load_session_entries` already drive every backend. `codepp-core`'s and `codepp-shell`'s suites cover the data-shape contract on every CI runner (true since CI widened to `cargo test --workspace`; see the test-discipline note below).
- **Untitled buffer survival** (the `<config_dir>/backup/` mechanism), **dirty saved-file backup**, **`SessionRestoreEntry::DirtyFromBackup`** with mtime-conflict detection, **`Shell::deferred_dialogs`** queue. All in `shell`. `platform::backups_dir()` already resolves the per-OS path.
- **Window size + maximized persistence.** `WindowGeometry` round-trips in session.xml; the platform applies its native equivalent of `SetWindowPos` + `ShowWindow(SW_SHOWMAXIMIZED)`.
- **Tab reorder logic.** `Shell::move_tab` and its 6 unit tests are platform-agnostic. Each backend wires the platform's drag-detection primitive (Win32 subclass + `WM_LBUTTONDOWN`/`MOUSEMOVE`/`LBUTTONUP`; GTK `GestureDrag`; Cocoa `NSResponder` mouse events) to call it.
- **`PendingDialog`** plumbing — `ConfirmReload` and `Error` dialogs are returned by `Shell::drain` and presented by the UI. Each backend just maps the two variants to its native dialog primitive.
- **File loading, encoding/EOL detection, file watching, find-in-files, plugin host, NPPM/NPPN dispatch.** All in `core` / `shell` / `plugin-host`; cross-platform from day one.

**Per-platform work for `ui_gtk` and `ui_cocoa` (the user-visible features Phase 5 must replicate):**

- **Main window chrome.** Menu bar (with mnemonic underlines), status bar (7-part layout matching the Win32 spring), toolbar (32 buttons across 10 separator-delimited groups, with the same SVG icon set under `assets/icons/`), tab strip.
- **Tab drag-to-reorder.** GTK: `GtkEventControllerLegacy` or `GestureDrag` on the `GtkNotebook` tab labels, hit-test → `Shell::move_tab`. Cocoa: `NSTabView` doesn't natively support drag-reorder; either subclass `NSTabViewItem`'s tracking area or build a custom tab strip on top of `NSScrollView` (matches what most Cocoa editors do).
- **Modal dialogs.** Goto, Find/Replace, FIF progress, About (with clickable home-page link + F1 binding), reload-confirm, error. Each platform has its own primitive — `GtkDialog` / `NSAlert` / `NSWindow` modal — but the *content shape* and the *trigger conditions* are documented by the existing Win32 implementations and by `PendingDialog`. Don't reinvent the UX; copy it.
- **Periodic auto-save.** Today on Win32 via `SetTimer` + `WM_TIMER` arm calling `Shell::save_session`. GTK uses `g_timeout_add(7000, …)`; Cocoa uses `NSTimer` scheduled for 7-second intervals. **Suggested abstraction** when the GTK backend lands: a new `UiPlatform::start_periodic(period_ms, callback)` returning a cancellation handle — would let `Shell` own the cadence and remove the timer-id constants from each backend, but keep the `WM_TIMER` arm in Win32 as the single subscriber.
- **Window-size restore.** Each platform applies its equivalent of `SetWindowPos(width, height) + ShowWindow(SW_SHOWMAXIMIZED)` from `Shell::saved_window_geometry()`. The toolbar-floor calculation is shared (`toolbar::natural_min_width_px` returns the inner width; the AdjustWindowRectEx step is platform-specific frame-chrome math that GTK/Cocoa replace with their own).
- **Drag-and-drop file open.** Win32 `DragAcceptFiles` / `WM_DROPFILES`. GTK `gtk_drag_dest_set` + `drag-data-received` signal. Cocoa `NSDraggingDestination` protocol on the main window.
- **Native open / save-as / folder-pick dialogs.** Win32 `GetOpenFileNameW` / `GetSaveFileNameW` / `SHBrowseForFolderW`. GTK `GtkFileChooserNative`. Cocoa `NSOpenPanel` / `NSSavePanel`.
- **Accelerators / hotkeys.** F1 → About, Ctrl+S → Save, Ctrl+W → Close, Ctrl+F/H → Find/Replace, Ctrl+G → Goto, Ctrl++/-/0 → Zoom, F3/Shift-F3 → Find Next/Prev. The list is in the Win32 `CreateAcceleratorTableW` block as the source of truth — GTK uses `GtkApplication::set_accels_for_action`, Cocoa uses `NSMenuItem.keyEquivalent`.
- **Per-tab document binding.** `UiPlatform::activate_tab(idx, scintilla_doc)` — Scintilla's `SCI_SETDOCPOINTER` is the same call regardless of host UI; only the editor-handle plumbing differs. The doc-pointer-swap helpers (`capture_text_from_doc`, `is_doc_dirty`) are mechanically the same on every platform.
- **Application icon, title bar.** Win32 embeds `code++.ico` via `app/build.rs`. GTK uses `gtk_window_set_icon_from_file` (or the GResource bundle). Cocoa picks up the icon from the `.app` bundle's `Info.plist`. The shared `assets/code++.png` source feeds all three (the `tools/codepp-app-icon/generate.py` extension point is documented in the script's docstring).

**Test discipline.** The whole workspace's tests run on every CI runner, so the backend-agnostic logic stays verified continuously. This was *not* true from Phase 0 as earlier revisions of this document asserted: CI ran `cargo test -p codepp-core` only, a line written when `core` was the sole crate with tests, so `shell`'s, `editor`'s and `udl`'s suites were verified on contributors' machines and nowhere else — and `ui_win32`'s 130 tests, being behind `#![cfg(target_os = "windows")]`, ran nowhere at all. Widened to `--workspace` in Phase 5. UI-level tests (e.g. "Phase 5 m1 demo: open the GTK build, drag a tab, restart, observe the new order persisted") are manual, gated on the §7.1 phase-rule end-of-phase demo. Don't bypass the demo.

## 8. Hard Performance Constraints

These are non-negotiable and verified at each phase boundary.

| Constraint | Budget | Verification |
| --- | --- | --- |
| Cold start (warm cache) to interactive | < 80 ms | Stopwatch from `WinMain` / `main` to first paint. Logged when `--perf` flag is set. |
| Single keystroke latency (typed char → Scintilla redraw) | < 5 ms p99 | Frame-time log on a 10k-line file. |
| Open 10 MB UTF-8 file | UI never blocks | Worker thread reads; marshal posts buffer to UI thread incrementally if needed. |
| Memory floor (one empty buffer) | < 25 MB **PSS** (proportional set size; private-resident is the fallback where PSS is unavailable) | Linux: `/proc/<pid>/smaps_rollup`. Windows: private working set from `GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`). macOS: `phys_footprint` from `task_vm_info`. |
| Undo history | Bounded, default 1000 ops, configurable | Scintilla `SCI_SETUNDOCOLLECTION` + periodic trim. |
| Plugin load on startup | Zero plugins loaded until first user interaction touches them | Trace log at startup shows zero `LoadLibrary` calls until menu open. |
| File I/O thread | Dedicated worker pool, never UI thread | Lints fail if `core::file` is called synchronously from a UI crate. |

**Why the memory metric is PSS and not RSS.** The original wording said "< 25 MB RSS", which was written and measured against Win32 and does not survive the move to a second platform. RSS counts every resident page a process can see, including read-only, file-backed shared-library text that is demand-paged from the page cache and shared with every other process using the same toolkit. That inflates the number by an amount that varies with how heavy the platform toolkit is, not with anything Code++ does — so the same binary "fails" on one OS and "passes" on another while costing the system an identical amount. PSS attributes shared pages proportionally and is the figure that reflects real cost; on the platforms without a PSS equivalent, private-resident is the closest analogue and is stricter, not looser. The budget number itself is unchanged at 25 MB.

**Measured, Phase 5 m3, release build, one empty buffer, x86_64 Linux + GTK 3.24:**

| Figure | Value | Note |
| --- | --- | --- |
| PSS | **11.5 MB** | the constraint above — 46% of budget |
| Private (clean + dirty) | 10.3 MB | of which 6.3 MB dirty |
| `Shared_Clean` | 27.0 MB | GTK / GDK / pango / cairo / glib library text, shared with every GTK process |
| RSS | 37.3 MB | PSS + the shared pages above; recorded for continuity with the old metric |

The shared-page cost is not avoidable by writing the UI layer differently: `libscintilla.a` alone has 305 distinct undefined `gtk_*` / `gdk_*` / `pango_*` / `cairo_*` / `g_object_*` symbols, because Scintilla's GTK backend is itself a GTK client. Any Linux build that links Scintilla maps the whole stack, whether the Rust above it is gtk3-rs, `gtk-sys`, or hand-written `extern "C"`.

**Where the growth came from — measured, not inferred.** The figure recorded at m1 was 8.5 MB PSS; the table above is 11.5 MB. That is past §8's own ">20% regresses the constraint" bar if read as measurement-over-measurement, even though the absolute figure is under half the budget. An earlier revision of this section guessed the cause ("the likely bulk is the lexer theme table"). That guess was wrong, and the measurement is below.

m1 (`e64f530`) and m3 (`HEAD`) were built and run back to back on the same machine with an empty session, and `/proc/<pid>/smaps` attributed per mapping:

| Bucket | m1 | m3 | Delta |
| --- | --- | --- | --- |
| binary `.text` | 0.89 MB | 3.49 MB | **+2.60 MB** |
| binary `.rodata` | 0.21 MB | 1.06 MB | +0.85 MB |
| shared libs | 2.21 MB | 2.33 MB | +0.11 MB |
| anonymous | 1.30 MB | 1.37 MB | +0.07 MB |
| **heap** | **3.46 MB** | **3.46 MB** | **±0.00 MB** |
| Total PSS | 8.17 MB | 11.81 MB | +3.64 MB |

Three things fall out of that, and only the third matches the old guess:

1. **71% of the growth is code, not data.** The theme table itself is `.rodata` — 85 `const` items that rvalue-promote when `lang_theme` hands out `&'static` references — and accounts for at most the +0.85 MB there, under a quarter of the total. What actually grew is `.text`: the whole of m2 and m3 (the `Shell` wiring, 34 `UiPlatform` methods, the status bar, the menus, session restore, the tab strip) plus the per-language theme *application* code, which is an 85-arm dispatch each issuing ~20 styling calls. Code, not tables.
2. **Heap did not move at all** — 3.46 MB at both ends, to the kilobyte. Nothing added between m1 and m3 allocates more at rest. Whatever this is, it is not a leak and it does not scale with what the user opens.
3. **So it is a one-off static floor rise**, which was the old conclusion, reached for the wrong reason.

Resident `.text` is 3.49 MB of 4.07 MB on disk (88%, up from 74% at m1), so this is not "the binary got bigger and the pages are idle" — startup genuinely executes most of it. Reducing it means executing less code at startup or generating less of it: `lang_theme`'s 85-branch `if` chain compiled to a table lookup, `opt-level = "s"` for the release profile, or `lto = "fat"` over the current `"thin"`. None has been tried; each is a measurable experiment rather than a guess.

**The decision this needs is recorded in §7.4.** The numbers above are the evidence for it: 11.8 MB against a 25 MB budget, with the growth being static code that does not scale with usage, and zero movement at runtime.

**Measured, Phase 5 m1, release build, one empty buffer, arm64 macOS 26.5 + Cocoa:**

| Figure | Value | Note |
| --- | --- | --- |
| `phys_footprint` | **73.0 MB** | the §8 metric on this platform — **292% of the 25 MB budget** |
| `phys_footprint` (peak) | 96.7 MB | during startup |
| Writable regions | 264.9 MB mapped, 68.5 MB resident, 16.9 MB actually written | |
| Library text | 1.8 GB mapped, 443 MB resident | all `SM=COW`, 0 K dirty — shared, clean, file-backed |

**This is the largest budget miss anywhere in the project and it is not yet explained.** Recorded rather than quietly deferred, and stated as unexplained rather than guessed at — §8's own history (the retracted frame-clock conclusion, the wrong "the theme table did it" attribution) is why guessing here would be a mistake.

What the attribution does show is suggestive but not conclusive. `vmmap` reports the process mapping **WebCore (57.6 MB), JavaScriptCore (26.9 MB), SwiftUI (23.3 MB), GeoServices (30.2 MB), Network (24.1 MB), ANECompiler (22.5 MB) and libusd_ms (29.5 MB)** — none of which a text editor has any use for, and none of which Code++ links against. They arrive through AppKit's own initialisation on this OS version. Two things stop that being the answer on its own:

1. Those are all clean `r-x` `SM=COW` text regions with **0 K dirty**, which is exactly the category `phys_footprint` is supposed to exclude — the same category §8's RSS→PSS switch exists to stop counting. So they should not be in the 73 MB, and the resident 443 MB of library text plainly is not.
2. The 68.5 MB of *resident writable* memory is the figure that actually needs explaining, and only 16.9 MB of it has ever been written. A large mapped-and-resident-but-mostly-untouched writable arena is more consistent with an allocator or framework reservation than with anything Code++ does with one empty buffer.

So the honest summary is: the metric says 73 MB, the budget says 25 MB, and the cause is a resident writable arena that has not been attributed to a caller yet. The next step is `malloc_history` / `heap` against a live process, not another `vmmap` summary. Tracked in §7.4.

One caveat on comparing this to the Linux row: `phys_footprint` and PSS are not the same quantity, so 73 MB vs 11.5 MB is not a like-for-like 6× — §8 deliberately specifies a different metric per platform because each OS exposes a different honest one. The comparison that matters is each figure against the shared 25 MB budget, and macOS is the one that fails it.

**What the 80 ms budget actually costs on this platform, and why the memory figure was misattributed for four milestones.** Prompted by the obvious follow-up question — *could a Cocoa app be written that comes close to the Win32 port?* — and answered by building the smallest possible one rather than reasoning about it. The reference is a twelve-line Objective-C program: `NSApplication`, one `NSWindow` at Code++'s own 1024×768, one `NSView` whose `drawRect:` fills white, and nothing else.

| | minimal Cocoa app | Code++ (m4b) |
| --- | --- | --- |
| `main()` → first paint | **149.7 / 182.9 / 195.0 ms** | ~235 ms |
| `phys_footprint` (settled) | **13.6 MB** | 76–77 MB |

**On cold start the answer is no, and not marginally.** An empty Cocoa window costs 150–195 ms to first paint on this machine, and Win32's *entire* cold start is 94 ms — below the macOS floor for a blank white rectangle. Code++'s own contribution is the difference, ~40–85 ms, and driving that to zero would still leave the platform floor. Instrumenting `_dyld_image_count` says where it goes: the process holds 517 images at `main`, `sharedApplication` adds **85** (AppIntents, RelevanceKit, CoreSpotlight, Contacts, ClassKit, CloudDocs, FileProvider, QuickLookThumbnailing…), and the stretch from `makeKeyAndOrderFront:` to the first `drawRect:` adds **420 more** — including **WebKit, WebCore, JavaScriptCore, libwebrtc, SafariServices, WebInspectorUI, WritingToolsUI** and the generative-assistant stack. A plain `NSView` filling one colour pulls in a browser engine and Apple Intelligence's UI layer, because on macOS 26 they sit behind the text/accessibility machinery every window initialises. Nothing in that is reachable from application code.

**On memory the answer is the opposite, and it overturns what §8 has said since m1.** The same minimal app settles at **13.6 MB**, so the ~77 MB is *not* an AppKit floor — roughly 63 MB of it is Code++'s. The reason it never moved across milestones is not that AppKit set it; it is that its dominant term depends on window size, which never changed. Attributed with `vmmap`, same window, same display:

| Region | minimal app | Code++ | |
| --- | --- | --- | --- |
| **IOSurface** | 3.3 MB | **46.2 MB** | window and layer backing store |
| `MALLOC_SMALL` (dirty) | 4.5 MB | 11.5 MB | real heap |
| CoreAnimation | 0.2 MB | 2.7 MB | |
| IOAccelerator | — | 3.9 MB | |

So **~60% of the macOS memory figure is GPU-shared backing store for the window and its layers**, not anything Code++ allocates — on a 2880×1864 Retina panel a full-window surface is ~12.6 MB on its own, and Code++ has eight of them against the minimal app's six much smaller ones. That also makes the cross-platform comparison unfair in a way §8 did not previously account for: on Linux the equivalent compositing buffers live in the X server, not in the editor's PSS, so the two numbers were never measuring the same thing. The leading candidate for why Code++'s surfaces are so much larger is already recorded in §7.4 — macOS 26's `SCIScrollView` carries a scroll-edge-effect `NSVisualEffectView` measured at 690 pt inside a 548 pt scroll view, and a visual-effect view forces layer backing on its subtree. Untested, and named as a candidate rather than a cause.

The earlier claim that 68.5 MB of resident writable memory was unexplained is therefore **retracted**: most of it is IOSurface, which `vmmap`'s writable-region summary counts and which is not heap at all.

**Correction, and it is the largest one in this section: every macOS memory figure recorded before this point was measured with the wrong buffer set, and the budget is not actually missed.**

§8's memory constraint says *one empty buffer*. The figures above — 73 MB at m1, 77 MB at m4b, and the 50 MB after the colour-space change — were all taken by launching the release binary and sampling it, which **restores the previous session**. By the time the m4b work was done that session held five files including a 10 000-line `.rs`, a `.log`, and a crash-recovery backup. Deleting `session.xml` first and re-measuring the *same binary*:

| Condition | `phys_footprint` | Cold start |
| --- | --- | --- |
| **One empty buffer — §8's stated condition** | **18.5 MB** | **165–170 ms** |
| One 10 000-line `.rs` open | 29.3 MB | ~159 ms |
| The accumulated session (5 files + a backup) | 76 MB | ~470 ms |

**So macOS meets the 25 MB memory budget at 18.5 MB, and has presumably done so since the colour-space change.** It was never re-measured under the stated condition, so the miss was reported for four milestones on the strength of a number that answered a different question. The 25 MB figure is a *floor* — what the editor costs before the user opens anything — and measuring it with a working session loaded is simply not that measurement.

Two things worth taking from it beyond the number. First, the ordering trap: the app restores its session *by design*, so on this platform "run the binary and read `phys_footprint`" silently measures whatever the developer last had open, and it drifts upward over a working day. Any repeat of this must clear `session.xml` first, and DEVELOPMENT.md now says so. Second, the retracted savings figure: the "77 MB → 50 MB, 35%" attributed to the sRGB pin below was a before/after across that same loaded session. Re-measured clean it is **18.9 MB → 18.5 MB**, because at idle with one empty buffer few compositing surfaces are live for the format change to halve. The **per-surface** halving is not retracted — it was observed directly, `RGhA` at 20.0 MB becoming `BGRA` at 10.2 MB — so the saving is real but scales with how many surfaces the compositor has allocated, which scales with what is on screen. Keep the pin; do not keep the headline number.

Cold start is unaffected by the correction in the direction that matters: ~167 ms against an 80 ms budget, still missed, but now sitting *inside* the 150–195 ms range a minimal Cocoa app takes to first paint. Code++'s own contribution to it is close to nothing.

**Following that up: the memory is compositing surfaces, and a one-line change removes a third of it.** The lead named above — the scroll-edge-effect `NSVisualEffectView` — was **tested and refuted**: removing all three of them from the live view tree saved nothing (47.4 MB either side). What the footprint actually tracks is window *area*: 27.6 / 47.8 / 70.3 MB at 400×300, 1024×768 and 1600×1200. Note the first of those — a 400×300 window is already over the 25 MB budget.

`vmmap`'s per-surface detail names the cause. Both Code++ and the minimal app hold one `CA Whippet Drawable` per buffer, and the difference is the *pixel format*:

| | surface | format | bytes/px | size |
| --- | --- | --- | --- | --- |
| minimal app | 2048×1600 | `A008` | 1 | 3.2 MB |
| Code++ (before) | 1926×1346 | **`RGhA`** | **8** | **20.0 MB** ×3 buffers |
| Code++ (after) | 1926×1346 | `BGRA` | 4 | 10.2 MB |

`RGhA` is half-float RGBA — the wide-gamut / EDR format CoreAnimation picks for a window on a display that can show more than sRGB, which is every recent Mac. **Pinning the window's colour space to sRGB drops it to 8-bit `BGRA`**, and `phys_footprint` from ~77 MB to **~50 MB, a 35% saving**, scaling with window area (70.3 → 49.9 MB at 1600×1200).

Nothing is lost, because Code++ has no wide-gamut content: the lexer themes are hex literals, Scintilla takes packed RGB, and the toolbar icons are sRGB PNGs — those values *are* sRGB, so a half-float pipeline cannot render them more accurately. Verified by rendering the same highlighted buffer either side of the change and comparing pixels: the dominant colours are identical to the pixel and the same counts (`ffffff` ×216 014, `e4e4e4` ×10 067, `1e1e1e` ×8 903), with ~26 antialiasing-edge pixels on coloured glyphs differing — which is inherent to blending in a different space, and now matches what the Win32 and GTK backends do. Two things that look equivalent and are not, both measured: `setDepthLimit(NSWindowDepthTwentyfourBitRGB)` changed nothing, and neither did `setOpaque(true)`.

**macOS after this change: `phys_footprint` 49.5 / 49.5 / 50.2 MB, cold start 246 / 250 / 253 ms.** Still 2× the memory budget and ~3× the cold-start one, but the memory figure is now the smaller of the two misses rather than the larger, and what remains of it is compositing buffers whose size is set by the window the user chose.

**macOS keystroke latency, measured for the first time.** The two missing hooks are now wired — `key_pressed` from a local `NSEvent` monitor (a monitor rather than a subclass: the pump is `-[NSApplication run]` and the view that receives keys is inside the vendored Scintilla tree, so neither backend's shape was available) and `text_modified` on `SCN_MODIFIED`. Driven by posting synthetic key events from a timer, 400 samples per row:

| Buffer | Input rate (measured) | p50 | p90 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| 10 000-line `.rs` | 8 char/s (125 ms gaps) | 5.12 ms | 18.67 ms | **20.56 ms** | 32.06 ms |
| Empty | 8 char/s (125 ms gaps) | 5.30 ms | 19.08 ms | **20.88 ms** | 32.42 ms |
| 10 000-line `.rs` | 20 char/s (50 ms gaps) | 3.91 ms | 10.91 ms | **11.64 ms** | 29.71 ms |
| 10 000-line `.rs` | ~7 char/s, jittered 128–156 ms | 5.32 ms | 18.15 ms | **20.27 ms** | 30.65 ms |

**p99 ≈ 20 ms against a 5 ms budget — 4× over, and the worst of the three backends** (GTK 4.62 ms, Win32 8.89 ms). Three properties, all measured rather than inferred:

1. **Content-independent.** An empty buffer and a 10 000-line lexed `.rs` file are identical to within noise, so Lexilla and buffer size are not involved — the same refutation GTK's dedicated test made.
2. **It gets *better* at twice the input rate** (p99 20.6 → 11.6 ms), which rules out queueing outright — the opposite of a backlog.
3. **The distribution is bimodal**, roughly half the samples near 5 ms and most of the rest near 19 ms.

The obvious objection — that a fixed 125 ms interval is exactly 7.5 frames and would alias against the 60 Hz refresh, pinning every keystroke to one of two phases — was **tested and refuted**: jittering the interval across 128–156 ms, a range wider than a frame, leaves the distribution unchanged. The bimodality is real, not a sampling artefact.

**Profiled, and the cause is not what the shape suggested.** An earlier revision of this section read the ~14 ms separation as close to a 60 Hz frame and concluded that some keystrokes make the current composite while the rest wait for the next. **That is retracted.** Splitting the interval and measuring main-thread CPU time across it says otherwise:

| | p50 | p99 |
| --- | --- | --- |
| key press → `SCN_MODIFIED` | **0.21 ms** | 0.45 ms |
| `SCN_MODIFIED` → `SCN_PAINTED` | 7.99 ms | **19.91 ms** |
| main-thread CPU *within* that window | 8.63 ms | 19.79 ms |

CPU time equals wall time to within 0.04 ms in both modes, so **the thread is busy for the entire interval — it is not waiting for a frame at all**. Scintilla's handling of the keystroke itself is free (0.2 ms); every millisecond is in the paint, and it is work.

`sample` names the work. The stack is `-[SCIContentView drawRect:]` → `ScintillaCocoa::Draw` → `SyncPaint` → `Editor::Paint` → `EditView::PaintText` → **`EditView::DrawLine`** → `DrawForeground` → `SurfaceImpl::DrawTextTransparent` → **`CTLineCreateWithAttributedString`**. So each paint re-runs CoreText line layout — typesetting, glyph encoding, the lot — and it does so for *many* lines rather than the one that changed.

**Confirmed by varying the window height**, which is the cleanest possible test of "how many visible lines":

| Window height | ≈ visible lines | p50 | p99 |
| --- | --- | --- | --- |
| 200 pt | 14 | 5.13 ms | **6.41 ms** |
| 500 pt | 35 | 11.09 ms | 14.28 ms |
| 900 pt | 64 | 10.89 ms | **21.09 ms** |

Latency scales with the number of visible lines. At 14 lines it is nearly inside the budget. **Every keystroke repaints every visible line.**

Four candidate causes were tested and **all four refuted**, which is worth recording so none is re-tried: the per-`SCN_MODIFIED` status-bar refresh (p99 20.1 vs 19.4 with it removed), Scintilla's `SC_CACHE_PAGE` layout cache (22.5 vs 21.9), `SC_PHASES_ONE` single-phase drawing (22.6), and this backend's own `SCN_PAINTED` hooks — the scroller-layout repair and the horizontal-width clamp (21.6 vs 21.7, with an identical fast/slow split). None of them is involved.

What is left is structural, and the stack shows it: `-[NSViewBackingLayer display]` → `_NSViewDrawRect` → `drawRect:`. The window is layer-backed — measured earlier at **169 of 169 views**, which is not a choice this backend makes, since `NSWindow`'s content view has been unconditionally layer-backed since 10.14 — and the layer redraw hands Scintilla the full bounds rather than the changed line's rect. Scintilla then does what it is asked and lays out every line in it.

**That fix is now implemented.** `crates/scintilla-sys/cxx/QuartzTextLayout.h` replaces the vendored header and memoises the `CTLine` on `(text, requested encoding, font, foreground colour)` — the complete set of inputs, since the style dictionary only ever carries a font and a foreground colour. Measured back to back at three window heights, the same binary with the cache toggled by `CODEPP_NO_CTLINE_CACHE`:

| Visible lines | p99 without | p99 with | p50 without | p50 with |
| --- | --- | --- | --- | --- |
| 14 | 5.03 ms | **4.00 ms** | 1.81 ms | 1.26 ms |
| 35 | 15.50 ms | **10.26 ms** | 10.73 ms | 7.66 ms |
| 64 | 22.78 ms | **15.59 ms** | 10.52 ms | 7.16 ms |
| 64, re-run after the audit's hardening | 18.07 ms | **13.78 ms** | 11.98 ms | 8.91 ms |

Read the *pairs*, not the absolute values: this machine's numbers drift with load across a long session — the last row was taken hours after the first three, and the untouched binary moved with it. Every pair above is back to back on one binary with `CODEPP_NO_CTLINE_CACHE` flipped, and the reduction is 24–34% wherever it is measured.

**Roughly a third off at every size, and inside the 5 ms budget at 14 visible lines.** Re-profiling confirms the intended effect and the remaining floor: `CTLineCreateWithAttributedString` is gone from the profile entirely, and what is left under `DrawTextTransparent` is `TLine::DrawGlyphs` → `CGContextDelegateDrawGlyphs` — actual glyph rasterisation, which is irreducible while every visible line is being redrawn. Closing the rest means partial invalidation, and the full-bounds repaint is AppKit's, not ours.

**It is carried without forking the submodule.** `build.rs` stages the vendored `cocoa/` sources into `OUT_DIR` and drops Code++'s header over the top, so the pinned checkout stays pristine and survives `git submodule update` — a patch applied in place would be silently reset by exactly that command. Two guards, both mutation-verified: `build.rs` fingerprints the upstream file it replaces and fails the build if a Scintilla bump changes it, and `scintilla_cocoa_ctline_cache_selftest` asserts that a repeated identical layout hits the cache. The second is deliberately **not** a latency assertion — timing on a shared runner would be flaky and would fail for reasons unrelated to the cache, whereas "did the second identical layout hit" is exactly the property the fix depends on, is deterministic, and needs no window server.

The other two backends never needed this, because neither re-typesets per paint: Win32 goes through GDI/DirectWrite and GTK through Pango, both of which cache internally.

One caveat on the method: the keystrokes are posted into the app's own event queue rather than delivered by the window server, so the arrival distribution is what `--perf` reports and not what a `--delay` flag claims — the same discipline the `xdotool` calibration note above establishes. The interval itself is unaffected: it opens when the monitor observes the event, which is at dispatch, not at post.

**The memory figure did not move at all**, and that is the most informative number in this table. m2 added `Shell` (with its loader and file-watcher worker threads), the 7-part status bar, three menus, the session restore path and the `NSTimer` auto-save — and the footprint is identical to three significant figures. Combined with m1's attribution (68.5 MB resident writable, only 16.9 MB ever written), that is strong evidence the 73 MB is a fixed arena established by AppKit's own initialisation rather than anything Code++ allocates, and that it will not scale with what the editor does. It does not make the budget miss acceptable — it makes it a single, findable cause rather than accumulated drift, which is the better of the two problems to have.

Cold start rose ~9 ms, which is what `Shell::new` (spawning the loader and watcher threads) plus session-file I/O plausibly cost, and is proportionate. The first run of each batch is discarded as cold-FS-cache (151 ms here), the same convention the Win32 row documents. Still ~50% over the 80 ms budget; tracked in §7.4.

**Cold start, measured with `--perf`** (which now exists — `main()` entry to first draw, in-process, so it excludes process spawn and dynamic linking but includes everything Code++ does):

| Platform | Session restored | Cold start |
| --- | --- | --- |
| Linux + GTK | Empty buffer | 39.5 ms |
| Linux + GTK | One 10 000-line `.rs` file | 49.5–50.1 ms |
| Windows + Win32 | Empty buffer | 94.2 ms (warm-cache steady-state across two consecutive runs; first-run 140.8 ms with a cold FS cache — outside §8's "warm cache" scope but recorded so anyone repeating the measurement knows to discard it) |

The Linux figures are comfortably inside the 80 ms budget, and the ~10 ms difference is the file load, which is what it should be. **The Windows figures are not** — a ~94 ms empty-buffer floor is 18% over the 80 ms target, and the file-load delta is small enough (~5 ms) that the loader dominates. §8's cold-start budget is missed on Win32; tracked in §7.4.

**The macOS figure is the worst of the three by a wide margin** — ~235 ms empty-buffer against an 80 ms budget, roughly 3× over. Two thirds of the *budget* is spent inside `NSApplication::sharedApplication` before Code++ builds anything, and an `.app` bundle does not change that (measured). The per-phase attribution and the retraction of the earlier, differently-measured figures are in the m4b block above. Tracked in §7.4 alongside the Win32 miss.

This is a different quantity from the Linux exec-to-window-exists figures recorded during m3 (13–22 ms) — that one starts earlier and stops earlier, and the two should not be compared.

**Keystroke latency, characterised.** `--perf` opens the interval at the key press, promotes it when Scintilla reports `SCN_MODIFIED`, and closes it at `SCN_PAINTED`. Linux is measured against a 10 000-line file on a real X11 session with a compositing window manager at 1920×1200/60 Hz — **not** under Xvfb, which has no vsync throttling and where an absent frame-clock floor would prove nothing. Windows is measured on a real Windows 11 session at the same refresh rate with DWM composition active (i.e. every user's default), driven with `SendKeys.SendWait` from a PowerShell harness — the tool's sync-per-key round trip is ~35 ms on its own, so the "20 char/s" Win32 row lands at 50 ms gaps by adding a 15 ms harness sleep, and the "7 char/s" rows add a 100 ms sleep on top of the same round trip. Both the round trip and the sleep are inputs to the arrival rate, and the arrival distribution reported by `--perf` is what should be believed rather than either number in isolation. Sample sizes are 1 000 per row, single-machine, single-run — thinner than the Linux section's multi-run refutation-tested methodology, and worth reading as such: the qualitative miss ("Win32 misses both budgets") is well above single-run noise, but the two-decimal figures below are not to be treated as gold-plated.

`--perf` also reports the **arrival** distribution — the gap between consecutive keystrokes — because a latency figure cannot be read without the input rate that produced it, and because it is the only way to audit a synthetic input tool. That turned out to matter twice over: see the calibration note below.

**The three macOS rows above are pre-`CTLine`-cache and are kept for the before/after.** The shipped figures are in the m4b block earlier in this section: p99 **15.59 ms** at 64 visible lines, **10.26 ms** at 35, **4.00 ms** at 14 — about a third off, and inside the budget only at the smallest of those. macOS latency depends on window height in a way the other two backends' does not, so a single row cannot represent it.

**The Linux figure meets the §8 budget at human typing rates** — p99 4.62 ms against 5 ms, 8% margin, backed by ~50 observations rather than the one or two an earlier 88-sample run could offer.

**The Windows figure does not.** Every row sits at p99 ≈ 7–9 ms, 40–80% over the 5 ms budget, and the shape is the reason the finding is worth trusting despite the thinner sample size: Win32's distribution is compact and uniformly shifted rather than tail-cliffed. Max lands at ~10 ms across all three rows, with the p50→max spread inside each row at 53–66% — a wider gap than "flat" would imply, but nothing like GTK's 42× p50-to-p99 at 20 char/s. 3 000 samples with no outlier above 10.13 ms is real evidence against a GTK-magnitude tail, though a rarer or smaller-magnitude one is not ruled out. Doubling the input rate (7 → 20 char/s) barely moves any percentile, which rules out queueing. Something happens *per keystroke* that costs ~5 ms above the Linux baseline, rate-independent. The two 7 char/s rows (empty vs. 10 000-line `.rs`) sit ~20% apart at p99, in the *faster-with-more-content* direction — the isolation isn't clean since a `.rs` file gets Rust highlighting per Phase 4.5 (so lexer state and buffer size both changed at once), so the delta is worth noting rather than dismissing but doesn't cleanly isolate a lexer-cost contribution the way GTK's refutation test did. The direct-call path is architecturally identical on both backends — see the "direct-call path is architecturally identical" paragraph later in this section — so the cost lives on the input-delivery / paint side, not in Scintilla. Candidates that would need a profiler to distinguish: DWM composition scheduling, the per-`SCN_UPDATEUI` chrome refresh cost (status bar's dynamic parts + toolbar state + doc-map sync, all `SendMessage` roundtrips), `TranslateAcceleratorW` running on the hot path, or Scintilla's Direct2D paint on a themed frame. Tracked in §7.4.

**The GTK tail is not queueing.** An earlier revision said it was, on the grounds that it grew with input rate. It does, but p50 and p90 barely move between the two Linux + GTK rows in the table above — p90 *improves* — while p99 goes up 14×. A backlog lifts the whole distribution; this is a sharp cliff affecting about 1% of keystrokes, so something specific and occasional stalls rather than the editor being uniformly slower. Two obvious causes were tested against the same protocol and **both refuted**:

| Hypothesis | Test | p99 | Verdict |
| --- | --- | --- | --- |
| The 7-second session auto-save blocks the UI thread | interval raised to 100 000 s | 65.4 ms | refuted — unchanged |
| Lexilla restyling a large region after an edit | same size file, plain text, no lexer | 60.5 ms | refuted — unchanged |

So the cause is neither the auto-save nor the lexer, and it is content-independent. Identifying it needs a profiler rather than more black-box runs; it is tracked in §7.4. It does not affect the budget verdict, because it does not appear at human rates — the 8 char/s row's *worst* sample was 17.8 ms, so nothing there came close to the cliff.

**Calibration: `xdotool --delay N` delivers a character every N/2 ms, not every N.** Its man page says "delay between keystrokes", which is what an earlier revision of this section believed. Measured two independent ways that agree to 0.1 ms: the in-process arrival distribution reports 125.8 ms at `--delay 250`, and wall-clocking the command externally gives 125.9 ms/char (and 50.9 ms/char at `--delay 100`). **Every input rate this section previously quoted was therefore 2× too low** — what was labelled "4 char/s, ordinary typing" was really ~8 char/s, and "40 char/s" was ~77. The latency figures were never wrong; only the axis they were plotted against. Anyone repeating these measurements should read the arrival row rather than trusting the flag.

**Correcting an earlier version of this section.** A previous revision reported p50 ≈ 6.9 ms and p99 ≈ 13–17 ms and concluded that the budget was unsatisfiable because GTK's vsync-locked frame clock imposed an ~8 ms floor. **That was wrong, and it was an instrumentation bug rather than a finding.** The first implementation kept only the most recent unpainted keystroke, so when several characters arrived within one frame it measured the *last* one and discarded the rest — throwing away the longest waits, reporting a partial frame's delay as if it were the whole distribution, and producing 180 samples where 264 characters had been typed. Per-keystroke sampling shows a p50 nearly ten times lower. The frame-clock reasoning was internally consistent and matched the numbers it was given, which is precisely why a wrong instrument is dangerous: it produced a confident, quantitative, plausible conclusion. The lesson is recorded rather than quietly deleted.

**How the interval is measured, on all three platforms.** A key press opens it, Scintilla's `SCN_MODIFIED` promotes it to a real measurement, and `SCN_PAINTED` closes it. The middle step is what makes it honest: plenty of keys repaint nothing — Escape, arrows, Home/End, a Backspace at position 0, anything on a read-only buffer — and a press committed without it would wait until some unrelated later paint, the caret blink included, closed it with a fabricated latency running to hundreds of milliseconds. It is also what makes **Tab, Enter and Backspace measurable**: they edit the buffer, but only sometimes, and an earlier character-class filter had to exclude them wholesale because it could not tell an editing key from an inert one. Ctrl chords stay excluded — §8 budgets a *typed character*, and a paste's redraw cost is a different quantity large enough to dominate the tail — while `Ctrl`+`Alt` is `AltGr` on many layouts and is not a chord.

Verified by driving the real app: ten typed characters give ten samples and stay at ten through ten Escapes, twenty navigation keys, or ten Ctrl chords; adding five Enters, five Backspaces or five Tabs gives fifteen.

GTK reaches both notifications by pulling the boxed `SCNotification` out of the `sci-notify` signal's third `GValue` with `g_value_get_boxed`, and Cocoa reads them from the shim's plain C callback, so all three measure the identical span rather than approximately the same one. The opening edge differs in shape but not in meaning: Win32 matches `WM_CHAR` in its own pump, GTK connects `key-press-event` to the Scintilla widget, and Cocoa uses a local `NSEvent` monitor — the pump there is `-[NSApplication run]` and the key-receiving view is inside the vendored Scintilla tree, so neither of the other two shapes was available. It previously closed on GTK's own `draw` signal, which fires *before* Scintilla paints and so ended the interval a frame's cairo work early. Every hook on the Win32 side is filtered to the main editor's `hwndFrom`, so a plugin's own Scintilla panel cannot consume a pending keystroke. The Win32 chain (`WM_CHAR` matched in the message pump, `SCN_MODIFIED` + `SCN_PAINTED` matched off `WM_NOTIFY.nmhdr`) now has been exercised; the table above is what it produces. 500 and 1 000-sample runs across an empty buffer and a 10 000-line file confirm every hook fires — the "did the filter fire?" concern the doc previously flagged is closed.

**On the direct-call path being architecturally identical across platforms:** it is — `ScintillaGTK::DirectFunction` is captured once by `EditorHandle::from_gtk_widget`, so calls *into* Scintilla cost the same on either backend. What differs is input delivery (`key-press-event` rather than `WM_CHAR`) and painting (cairo rather than GDI/Direct2D). Both backends now have measurements — GTK at p50 ≈ 1.5–1.9 ms inside the budget, Win32 at p50 ≈ 6 ms outside it — and the size of the gap is the empirical proof that the "direct-call path is identical, therefore performance is similar" reasoning does not extend past the direct-call itself. Everything before Scintilla sees the keypress (message pump, accelerator translation) and after it emits the paint (composition, chrome refresh) diverges enough between the two backends to produce a 3× difference in per-keystroke median cost, on an otherwise identical Rust codebase.

If a future feature breaks any of these, it must either be feature-gated (off by default) or be redesigned. No exceptions for "minor" regressions.

## 9. Build, Packaging, CI

### 9.1 Build

- `cargo build -p app` produces `code++.exe` (Windows) / `code++` (Linux/macOS).
- All native code (Scintilla, Lexilla) is statically linked. The binary depends only on system libraries (`user32`/`kernel32` on Windows, `libgtk-3` on Linux, `Cocoa.framework` on macOS).
- Release profile: `lto = "thin"`, `codegen-units = 1`, `panic = "abort"`, `strip = "symbols"` (debug symbols extracted to a side file for crash decoding).

### 9.2 Distribution

- Windows: a single `.exe` plus a `plugins/` folder. Optional MSI installer in a later phase.
- Linux: tarball + AppImage. `.deb`/`.rpm` later.
- macOS: `.app` bundle with code signing in a later phase.

### 9.3 CI

- **Hosting:** the canonical repository is on Forgejo at <https://git.fiedler.live/tux/code-plus-plus>. A read-only mirror is pushed to GitHub. CI runs on Forgejo Actions only; the GitHub mirror has no workflow.
- **Runners:** three self-hosted Forgejo runners with labels `windows`, `linux`, and `macos`. Both the `build` and `lint` jobs use `runs-on: ${{ matrix.runner }}` to fan out across all three labels. The `fmt` and `cargo-deny` jobs run on the `linux` runner only — rustfmt is deterministic across platforms and cargo-deny inspects the workspace manifest, neither benefits from re-running per OS.
- **Why clippy on every platform:** the codebase's per-OS code is heavy (`ui_win32` is Windows-only today; `ui_gtk`/`ui_cocoa` join in Phase 5). A Linux-only clippy run silently accepts dead Windows-cfg code on the Linux/macOS paths; a Windows-only clippy run does the symmetric thing for the Linux/macOS UI backends. Running clippy on every platform means a missing cfg gate or a stale platform-specific lint produces a CI failure on the platform that observes the dead code, not at Phase 5 bring-up time.
- **Required jobs:** `cargo build --workspace --all-targets` on each runner, `cargo test --workspace --all-targets` on each runner, `cargo clippy --workspace --all-targets -- -W clippy::pedantic -D warnings` on each runner, `cargo fmt --check` (linux), `cargo deny check` (linux). The `clippy::pedantic` lint group is gated as denied — every pedantic finding must be explicitly addressed (hand-fixed or suppressed at the smallest reasonable scope with a documented rationale; bulk-category file-level `#![allow(...)]` blocks are accepted where they reflect a structural design choice — see e.g. the FFI-cast allows in `ui_win32` / `editor` / `plugin-host` / the plugin crates).
- **Windows job** additionally runs the Notepad++ plugin compatibility smoke test from Phase 3 onward.
- **Permissions:** workflows declare `permissions: contents: read` at the workflow level.
- **Hardening for self-hosted runners** (these are deliberate decisions enforced from Phase 0 onward, not deferrable):
  - `actions/checkout` is pinned to a commit SHA, never a floating tag. A tag-move supply-chain attack on persistent self-hosted hardware has durable impact (host-disk access, credential exfiltration, pivot to the local network), so SHA-pinning is mandatory. The bump procedure (`git ls-remote ... | update SHA + comment`) lives next to the pin in the workflow file.
  - `actions/cache` is **not used.** Persistent on-disk `target/` and `~/.cargo` provide the natural caching; the cache action's `restore-keys` prefix fallback is a cross-PR poisoning vector.
  - `cargo-deny` is installed via `cargo install --locked cargo-deny`, not via `EmbarkStudios/cargo-deny-action`. Removes the dependency on the Forgejo instance's external-action proxy and one more SHA to track.
- **Phase boundary:** tag the commit (`phase-0-complete`, `phase-1-complete`, ...) only after CI is green on all three runners and the phase demo is recorded.
